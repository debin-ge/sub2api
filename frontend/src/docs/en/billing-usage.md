# Billing and Usage

{{SITE_NAME}} billing and usage views depend on the current deployment's groups, channel pricing multipliers, quota parameters, and admin policies. Because different deployments may adopt significantly different billing rules, this page only explains the general core concepts users should understand for integration and reconciliation.

---

## How Usage Is Generated

| Usage Item | Detailed Description |
| :--- | :--- |
| **Input Tokens (Prompt)** | Includes the system prompt, conversation history, user input, tool definitions, and other content sent to the model. |
| **Output Tokens (Completion)** | Text, tool call arguments, or structured JSON generated by the model's reasoning. |
| **Image/Multimodal Capabilities** | Image generation, editing, or vision input, usually billed by image count, resolution, or upstream pricing. |
| **Embeddings** | Usually counted by input text tokens or API request volume. |
| **Retries** | Automatic client retries on failure or timeout are seen as new independent requests by the gateway, creating multiple charges. |

> [!NOTE]
> **Streaming Requests Billing**: Streaming responses (SSE typewriter effect) only change how data is returned to the client; **they do not mean requests are free or cheaper**. As long as the upstream model generates and returns content to the gateway, even if the connection is cut mid-way, the generated tokens are still counted.

---

## Dimensions Affecting Unit Price

| Dimension | Impact Mode |
| :--- | :--- |
| **Model Version** | Large price tiers exist between different models (input and output prices are usually different). |
| **Group** | Admins can configure different channel weights, price markups, and initial quotas for different users, environments, or teams. |
| **Channel** | The same model routed through different upstream channels/accounts may have different actual costs and availability. |
| **Model Mapping** | When requests are mapped to higher or lower level upstream models, it affects the final charge. |
| **Request Parameters** | `max_tokens` settings, batch input sizes, and image resolution levels will affect final cost. |

> [!IMPORTANT]
> **Reconciliation Reference**: If you have questions about billing, please log in to the current deployment console to check detailed billing records, or follow the specific rate rules provided by your admin.

## Cost Estimation Before Requests

Before launching a service, we recommend using these practices to reduce cost uncertainty:
1. Evaluate the task difficulty first, and choose higher cost-performance lightweight models where possible.
2. Trim conversation history to send only the core context, reducing input token redundancy.
3. Enforce a `max_tokens` limit in your code to prevent models from generating excessively long runaway responses.
4. For large documents, truncate, summarize, or chunk them locally before sending.
5. Send a few test requests with real prompts and check the dashboard billing records to measure the average cost.

> [!TIP]
> If the Anthropic-compatible token counting endpoint is enabled in your deployment, you can check token counts via:
>
> ```bash
> curl "${BASE_URL}v1/messages/count_tokens" \
>   -H "Authorization: Bearer $YOUR_KEY" \
>   -H "Content-Type: application/json" \
>   -d '{
>     "model": "claude-3-5-sonnet-latest",
>     "messages": [
>       { "role": "user", "content": "Estimate the tokens for this request." }
>     ]
>   }'
> ```

## Viewing Usage

In most cases, the platform console provides usage overview and billing detail pages where you can track the following metrics:

| Key Field | Metric Meaning |
| :--- | :--- |
| **Time** | Exact timestamp of the request or the statistical aggregation window. |
| **Model** | Requested model name and the actual underlying model name routed by the gateway. |
| **Input/Output Tokens** | Number of Prompt Tokens and Completion Tokens consumed by the request. |
| **Status** | Success, failure, or block status (due to insufficient balance, upstream error, rate limit, etc.). |
| **Cost** | Real consumption calculated based on the group and channel pricing rules. |

## Reconciliation and Anomaly Investigations

> [!WARNING]
> **Security Warning**: If you notice abnormal consumption rates, **never send screenshots or raw text containing your full API Key** when contacting support or submitting a ticket.
>

Please provide the following masked/de-sensitized clues instead:
1. Exact time range when the abnormal consumption occurred.
2. The name of the API Key, or only its last 4 characters.
3. The request path and model name generating high-frequency calls.
4. The environment name where the client or service is deployed.
5. Error codes and concurrency levels recorded in your error logs.
6. Whether any recent deployments include auto-polling, auto-retries, or loop logic.

## Account Budget and Safety Guidelines

For production systems, we recommend the following configurations before integration:

| Security Measure | Actionable Suggestion |
| :--- | :--- |
| **Multi-Environment Key Isolation** | Use strictly different API Keys for development, staging, and production. |
| **Daily/Monthly Spending Limits** | Configure daily or monthly quota limits for specific API Keys or groups in the console. |
| **Alert Thresholds** | Turn on notifications for low balance or high consumption speed alerts. |
| **Model Allowlist** | Only enable models needed by the application for the API Key to avoid misuse of high-cost models. |
| **Release Monitoring** | Monitor request frequency and cost curves in the console for 30–60 minutes after releasing new features. |
