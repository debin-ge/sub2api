# API Key 与账户

文档页面可以公开查看，但调用 {{SITE_NAME}} 接口需要有效的 API Key。API Key 决定了你能访问哪些模型、端点、分组额度和计费策略，因此接入前应先确认密钥来源、权限范围和安全保存方式。

## 登录与调用权限

| 场景 | 是否需要登录 | 说明 |
| --- | --- | --- |
| 查看文档 | 否 | 文档用于帮助用户接入，未登录也可以查看。 |
| 进入控制台 | 是 | 控制台通常用于查看账户、密钥、用量或管理信息。 |
| 调用 API | 需要 API Key | API 请求通过请求头认证，不依赖浏览器登录态。 |
| 切换模型或端点 | 需要密钥权限 | 可用范围由 API Key 所属分组和管理员配置决定。 |

如果你已经登录控制台，但命令行请求仍返回 401，说明请求没有带上正确的 API Key。浏览器登录状态不会自动传递到 API 调用中。

## 获取 API Key

API Key 一般来自管理员或控制台的密钥页面。拿到密钥后，先确认以下信息：

1. 密钥是否已启用。
2. 密钥所属用户或项目是否正确。
3. 密钥是否绑定有效分组。
4. 分组是否开放你需要的模型和端点。
5. 是否存在额度、余额、过期时间或速率限制。

如果你无法在控制台看到密钥，请联系管理员确认当前账号是否有创建或查看密钥的权限。

## 推荐环境变量

本项目文档统一使用以下环境变量：

```bash
export API_KEY="在这里粘贴你的API密钥"
```

后续请求统一使用：

```bash
curl "{{BASE_URL}}v1/models" \
  -H "Authorization: Bearer ${API_KEY}"
```

如果某个 SDK 要求 Base URL 指向 `/v1`，可以单独设置：

```bash
export OPENAI_BASE_URL="{{BASE_URL}}v1"
export OPENAI_API_KEY="${API_KEY}"
```

## 请求头格式

推荐使用 Bearer Token：

```http
Authorization: Bearer ${API_KEY}
```

常见错误包括：

| 错误写法 | 问题 |
| --- | --- |
| `Authorization: ${API_KEY}` | 缺少 `Bearer` 前缀。 |
| `Bearer API_KEY` | 传入了字符串字面量，没有读取环境变量。 |
| `Authorization: Bearer` | 密钥为空，通常是环境变量未设置。 |
| 在浏览器前端硬编码密钥 | 会泄露密钥，不适合生产使用。 |

## 权限与模型列表

同一个部署中，不同 API Key 看到的模型列表可能不同。推荐先用当前密钥查询：

```bash
curl "{{BASE_URL}}v1/models" \
  -H "Authorization: Bearer ${API_KEY}"
```

如果没有看到预期模型，优先检查：

1. 当前密钥是否属于正确分组。
2. 分组是否开放该模型。
3. 管理员是否配置了模型映射。
4. 对应渠道是否启用且可用。
5. 价格、额度或过期时间是否阻止请求。

## 密钥安全建议

| 建议 | 说明 |
| --- | --- |
| 放在服务端环境变量 | 不要把真实密钥写入前端代码、移动端包或公开仓库。 |
| 按项目拆分密钥 | 为不同应用、环境或团队创建独立密钥，便于撤销和排查。 |
| 定期轮换 | 当成员离开、仓库泄露或环境迁移时，应更新密钥。 |
| 最小权限 | 只开放业务实际需要的模型和端点。 |
| 日志脱敏 | 记录请求 ID、模型、错误码即可，不要记录完整密钥。 |

## 轮换密钥

安全轮换通常按以下顺序执行：

1. 创建新 API Key。
2. 在测试环境切换到新密钥，并调用 `/v1/models` 与最小请求验证。
3. 在生产环境更新密钥配置。
4. 观察请求成功率、延迟和用量。
5. 确认没有旧流量后，禁用旧 API Key。

如果你怀疑密钥泄露，应先禁用或重置密钥，再排查访问日志和异常用量。

## 自检命令

把下面命令作为密钥可用性的最小检查：

```bash
test -n "${API_KEY}" && \
curl -i "{{BASE_URL}}v1/models" \
  -H "Authorization: Bearer ${API_KEY}"
```

预期结果是返回 `200`，并包含当前密钥可访问的模型列表。若返回 401、403 或空列表，请参考错误排查页面继续定位。
