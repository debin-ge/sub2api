# API Key 与账户

文档页面可以公开查看，但调用 {{SITE_NAME}} 接口必须拥有有效的 API Key。API Key 决定了您能访问的模型集合、接口端点、分组额度和计费策略，因此在接入前应确认密钥来源、权限范围与安全保存方式。

---

## 登录与调用权限

| 场景 | 是否需要登录 | 说明 |
| :--- | :--- | :--- |
| **查看文档** | 否 | 文档用于帮助用户快速接入，未登录状态下亦可正常公开查看。 |
| **进入控制台** | 是 | 控制台主要用于查看个人账户、密钥管理、消费账单、模型映射或管理端点。 |
| **调用 API 接口** | 需要 API Key | 接口请求通过 HTTP 请求头承载 Token 凭证认证，不依赖控制台的浏览器登录态。 |
| **切换模型/端点** | 需要密钥权限 | 可调用的上游范围由 API Key 所属的分组和管理员配置动态决定。 |

> [!IMPORTANT]
> **关于 401 报错**：如果您已经登录了控制台，但在命令行中发出请求仍然返回 `401 Unauthorized` 错误，说明您的请求未正确携带 API Key。**浏览器的登录状态不会自动传递到 API 请求中。**

---

## 获取 API Key

API Key 通常来自管理员的直接分配，或者在平台控制台的密钥管理页面自主创建。在拿到密钥后，建议优先确认以下信息：
1. 密钥在控制台中是否处于 **启用** 状态。
2. 密钥所属的用户、项目或部门分组是否正确。
3. 密钥是否正确绑定了有效的 **分组**。
4. 绑定的分组是否开放了您所需要的具体模型和兼容端点。
5. 当前账号是否存在额度限制、欠费停机、速率限制或已过期。

## 推荐环境变量

本项目文档示例中，统一使用以下两个环境变量：

```bash
export BASE_URL="{{BASE_URL}}"
export YOUR_KEY="replace-with-your-api-key"
```

后续的最小验证请求统一推荐使用：

```bash
curl "${BASE_URL}v1/models" \
  -H "Authorization: Bearer $YOUR_KEY"
```

如果您使用的第三方 SDK 强制要求 Base URL 必须指向 `/v1` 结尾，可以单独将其导出为：

```bash
export OPENAI_BASE_URL="{{BASE_URL}}v1"
export OPENAI_API_KEY="$YOUR_KEY"
```

## 请求头格式

建议统一使用标准 HTTP Bearer Token 规范传递密钥：

```http
Authorization: Bearer $YOUR_KEY
```

> [!WARNING]
> 请注意规避以下几种在开发中常见的**请求头配置错误**：

| 错误配置示例 | 潜在问题 | 排查建议 |
| :--- | :--- | :--- |
| `Authorization: $YOUR_KEY` | 缺少了 `Bearer ` 前缀和空格。 | 请核对字符串，在 Token 前补全 `Bearer `。 |
| `Bearer YOUR_KEY` | 误将环境变量名当做字面量值直接写入了请求头。 | 请在运行环境里解析读取真实的密钥值。 |
| `Authorization: Bearer` | 传入的密钥内容为空。 | 通常是由于系统环境变量没有被成功导出。 |
| **在前端/浏览器端硬编码密钥** | 会导致密钥彻底泄露，存在安全隐患。 | 绝不可在生产的前端应用里暴露您的 API Key。 |

## 权限与模型列表

在同一个 {{SITE_NAME}} 部署节点中，不同的 API Key 所能访问的模型可能各不相同。建议您使用当前密钥执行以下查询以确认可用范围：

```bash
curl "${BASE_URL}v1/models" \
  -H "Authorization: Bearer $YOUR_KEY"
```

> [!TIP]
> 如果该命令返回的模型列表中没有看到您期待的模型，请协助排查以下项：
> 1. 当前密钥是否归属于正确的用户分组。
> 2. 分组对应的模型访问白名单是否包含该模型。
> 3. 后台是否针对该模型名称配置了映射与改写。
> 4. 对应的物理中转渠道目前是否在线且状态可用。

## 密钥安全建议

| 建议 | 说明 |
| :--- | :--- |
| **仅在服务端存储** | 密钥请存放在服务端的环境变量中，切勿放入前端打包代码、移动端 IPA/APK 或公开的代码库中。 |
| **按项目隔离密钥** | 尽量为不同的微服务、开发环境或外部团队创建独立的 API Key，方便按需独立封禁和排查账单。 |
| **定期安全轮换** | 遇到员工离职、临时调试环境迁移或可能发生数据泄露时，应在第一时间重新生成密钥。 |
| **最小权限原则** | 只为分组授予业务中实际会调用到的模型与端点，防范意外盗刷损失。 |
| **日志自动脱敏** | 日志系统只需记录请求 ID (Request ID)、模型名和错误状态，绝不要把完整的 API Key 打印到输出中。 |

## 轮换密钥

在生产环境无缝轮换 API Key 建议遵循以下标准步骤：
1. 登录控制台，新建一个全新的 API Key。
2. 先在开发/测试环境中切换为新密钥，调用 `/v1/models` 端点并完成一次最小聊天请求以验证其可用性。
3. 将新密钥配置写入生产环境并平滑热重载。
4. 观察后台接口调用流量，确认有新密钥的用量上升，且请求成功率正常。
5. 确认旧密钥在 24~48 小时内已无任何残留流量，在控制台正式禁用或物理删除旧密钥。

> [!CAUTION]
> 如果您怀疑密钥发生泄露，应在第一时间进入控制台**停用或直接删除**该 API Key，避免产生不必要的资金损失，然后再行排查安全漏洞。

## 自检命令

您可以将下述命令作为检测密钥可用性的黄金脚本：

```bash
test -n "$YOUR_KEY" && \
curl -i "${BASE_URL}v1/models" \
  -H "Authorization: Bearer $YOUR_KEY"
```

预期结果为返回 `HTTP/1.1 200 OK`，且响应体中包含模型 JSON 列表。如果返回了 401、403 或空数组，请前往文档的“错误排查”一章。
