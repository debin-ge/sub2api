# 最佳实践

本页面向把 {{SITE_NAME}} 接入业务系统的用户。目标是让调用稳定、可排查、成本可控，并减少密钥和配置风险。

## 接入前检查

| 检查项 | 建议 |
| --- | --- |
| Base URL | 使用 `{{BASE_URL}}` 或管理员提供的完整地址。 |
| API Key | 使用 `${API_KEY}` 环境变量，不要写入源码。 |
| 模型列表 | 先调用 `/v1/models` 确认当前密钥可访问模型。 |
| 端点格式 | 根据客户端选择 OpenAI、Anthropic、Gemini 或 Antigravity 格式。 |
| 最小请求 | 先跑通一条非流式最小请求，再接入业务逻辑。 |

## 配置管理

把配置集中放在环境变量或安全配置系统中：

```bash
export API_KEY="在这里粘贴你的API密钥"
export OPENAI_BASE_URL="{{BASE_URL}}v1"
export OPENAI_API_KEY="${API_KEY}"
```

建议测试、预发、生产使用不同 API Key，并在日志中记录环境名称、模型名和请求路径，便于排查。

## 模型选择

不要只按模型名选择，应结合任务类型、成本、上下文长度、延迟和稳定性：

| 任务 | 建议 |
| --- | --- |
| 分类、标签、简单改写 | 优先低成本、低延迟模型。 |
| 长文总结、复杂推理 | 选择上下文更长、推理能力更强的模型。 |
| 代码生成或修复 | 优先支持 Responses 或代码客户端适配良好的模型。 |
| 高并发场景 | 选择稳定渠道，并准备备用模型。 |
| 严格格式输出 | 使用低温度、明确 schema 或后处理校验。 |

上线前应让管理员确认模型映射和备用渠道，避免上游变更时业务不可用。

## 错误处理与重试

| 状态 | 建议 |
| --- | --- |
| 401 | 不重试，检查 API Key 和请求头。 |
| 403 | 不盲目重试，检查分组权限、额度和模型开放情况。 |
| 404 | 检查路径、Base URL 拼接和模型名。 |
| 429 | 使用指数退避，降低并发，限制最大重试次数。 |
| 5xx | 短暂退避后重试，并记录请求时间、模型和错误信息。 |

对会产生副作用的业务流程，不要无条件重放请求。需要重试时应在业务层保证幂等性。

## 流式输出

流式适合长文本、聊天界面和需要快速首字响应的场景。使用前确认：

1. 客户端支持 SSE 或流式读取。
2. 反向代理不会缓冲响应。
3. 超时时间足够覆盖长输出。
4. 用户取消请求时，客户端能正确关闭连接。
5. 失败时有非流式或重试降级方案。

流式失败不一定是模型问题，代理和客户端读取逻辑更常见。

## 成本控制

| 做法 | 说明 |
| --- | --- |
| 限制 `max_tokens` | 控制输出上限，避免超长生成。 |
| 裁剪上下文 | 只发送必要历史和资料。 |
| 分级模型 | 简单任务走低成本模型，复杂任务再升级。 |
| 控制并发 | 避免批处理或定时任务瞬间打满额度。 |
| 监控重试 | 失败请求大量重试会放大成本。 |

发布新功能后，应观察用量曲线和失败率，确认没有循环调用或异常重试。

## 日志与排查

建议记录：

1. 请求时间和耗时。
2. 请求路径和模型名。
3. 状态码和错误摘要。
4. 客户端版本或服务名称。
5. 请求 ID、用户业务 ID 或任务 ID。

不要记录完整 API Key、完整用户隐私数据或大段敏感提示词。需要给管理员排查时，提供时间点、模型、路径、错误码和脱敏后的请求摘要即可。

## 生产上线清单

上线前确认：

- API Key 已按环境隔离，并有轮换方案。
- `/v1/models` 返回的模型符合预期。
- 关键端点已完成最小请求验证。
- 429 和 5xx 有退避重试。
- 401、403、404 能给用户明确错误提示。
- 日志已脱敏，并能关联请求和业务任务。
- 成本、额度或失败率有监控入口。
- 有备用模型或人工处理方案。
