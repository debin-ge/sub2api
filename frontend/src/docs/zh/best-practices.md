# 最佳实践

本指南面向将 {{SITE_NAME}} 接入生产和业务系统的开发者。目标是实现调用高可用、可快速定位故障、成本可控，并有效避免凭证泄露风险。

---

## 接入前上线清单

| 检查项 | 最佳实践建议 |
| :--- | :--- |
| **Base URL** | 统一配置为 `{{BASE_URL}}`，并视客户端 SDK 种类决定是否追加 `/v1`。 |
| **API Key** | 必须通过系统环境变量传入，切勿直接以字符串字面量硬编码进代码中。 |
| **模型白名单** | 接入前调用 `/v1/models`，确认当前 Key 实际拥有该模型的访问权限。 |
| **端点匹配** | 选择与客户端库最契合的 API 端点族（OpenAI/Claude/Gemini/Antigravity）。 |
| **最小可行性** | 先确保一次非流式 (Non-stream) 最小请求成功，再开发业务逻辑。 |

## 配置与环境管理

建议将网关配置集中在服务端的环境变量或受保护的安全配置中心中：

```bash
export BASE_URL="{{BASE_URL}}"
export YOUR_KEY="replace-with-your-api-key"
export OPENAI_BASE_URL="{{BASE_URL}}v1"
export OPENAI_API_KEY="$YOUR_KEY"
```

> [!TIP]
> **多环境密钥隔离**：强烈建议测试、预发和生产环境使用完全不同的 API Key。在日志中记录环境名称、调用的模型以及请求路径，可以极大地加速生产环境的故障排查。

## 模型选用策略

选择模型时，应综合衡量任务特征、单次成本、上下文大小、响应延迟和通道稳定性：

| 业务场景 | 模型选择建议 |
| :--- | :--- |
| **文本分类、改写、简单清洗** | 优先选用低成本、响应极速的轻量级模型。 |
| **长文总结、深度分析推理** | 选用推理能力更强、上下文窗口更宽的旗舰级模型。 |
| **代码生成、代码审查 (IDE)** | 优先使用针对代码格式特化、完美兼容 Responses API 的模型。 |
| **高并发在线业务** | 确保后台有多条备用渠道，并在客户端实现模型容灾退避。 |
| **结构化 JSON 格式输出** | 建议配置低温度系数 (`temperature <= 0.2`)，并采用后处理校验。 |

## 错误处理与指数退避重试

在对接中，应针对不同的 HTTP 状态码实施差异化的异常处理逻辑：

| HTTP 状态码 | 客户端重试策略 | 处理机制与排查方法 |
| :--- | :--- | :--- |
| **401 Unauthorized** | 🚫 **绝不重试** | 检查 API Key 变量是否配置成功，Bearer 前缀是否漏写。 |
| **403 Forbidden** | 🚫 **不盲目重试** | 密钥有效但所在的分组未配置该模型或已欠费。 |
| **404 Not Found** | 🚫 **绝不重试** | 确认 API 端点子路径拼装正确，以及模型名无拼写错误。 |
| **429 Too Many Requests** | ✅ **指数退避重试** | 降低瞬时并发，加入随机抖动延时，限制最大重试次数。 |
| **5xx Server Error** | ✅ **短暂延时后重试** | 结合指数退避进行 2-3 次重试，并记录发生时间和错误详情。 |

> [!IMPORTANT]
> **重试幂等性**：对于在数据库侧会产生写操作或扣费副作用的业务流程，切勿进行无条件无限重试。请在业务层通过引入唯一请求标识 (Request ID) 来实现重试幂等。

## 流式输出 (SSE) 规范

流式输出能带来极佳的首字响应体验。在客户端启用流式输出前，请先核对：
1. 确认前端应用有良好的流式解析逻辑（如能够正确处理 `data: [DONE]` 标志）。
2. 确认沿途的网络反向代理（如 Nginx、Cloudflare 等）已**关闭了 Buffer 缓冲功能**，支持流式实时透传。
3. 确保客户端和 HTTP 连接超时时间（Read Timeout）被设置为足够长的阈值，以应对大长文本推理。
4. 用户主动中断/关闭页面时，客户端应用能正确向中转网关发送 TCP RST 信号关闭 HTTP 链接，避免后台计费浪费。

> [!NOTE]
> 流式输出失败时，很多时候不是大模型上游异常，而是因为代理服务器超时设置过短或者客户端 SSE 解析器由于特殊字符中断。

## 降本增效与治理

* **限制 `max_tokens`**：为请求显式指定合理的输出长度上限，防范由于 Prompt 注入或模型死循环导致的大额 Token 浪费。
* **精炼上下文 (Context Trim)**：及时裁剪冗余的历史对话，只向模型发送核心的上下文信息。
* **多级模型调度**：简单意图识别走低成本模型，确认需要复杂计算时，再通过逻辑判断将请求转给旗舰模型。
* **平滑瞬时并发**：避免让批量离线任务或定时 Cron Job 在同一时刻爆发调用，防止额度瞬间耗尽或触发 429 报错。

> [!WARNING]
> 发布新功能后，必须密切关注后台的调用用量曲线和异常成功率。防范由于代码层 bug（如递归调用、无限循环重试）导致的资金损失。

## 生产上线自检清单

- [ ] **环境隔离**：生产与测试密钥已物理隔离，且在内部有定期的密钥轮换机制。
- [ ] **模型确认**：在生产网络中运行 `/v1/models`，返回的模型白名单符合预期。
- [ ] **最小请求验证**：在业务环境对关键端点进行了成功的非流式和流式网络验证。
- [ ] **重试机制**：已在应用中对 429 和 5xx 错误实现了带有随机抖动的指数退避（Exponential Backoff）重试。
- [ ] **错误友好性**：当遭遇 401、403、404 时，客户端能够向最终用户返回直观的文字提示，而不是硬编码的报错日志。
- [ ] **日志脱敏**：日志中仅记录 Request ID、时间、模型名和响应码，已脱敏所有 API Key 及用户敏感数据。
- [ ] **兜底手段**：已针对高风险或核心支付业务设计了人工兜底或后备模型容灾机制。
