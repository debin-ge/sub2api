# 错误排查

{{SITE_NAME}} 错误可能来自网关本身，也可能来自上游平台。排查时先确认 Base URL、API Key、端点路径、模型名和当前分组权限，再判断是否需要联系管理员。

---

## 排查步骤

建议按照以下顺序逐步定位问题：

1. 用当前环境变量调用 `/v1/models`，确认密钥和基础网络正常。
2. 用同一个模型发起非流式最小请求。
3. 如果非流式成功，再验证流式请求或业务请求。
4. 对比本地、测试、生产的 Base URL、API Key、模型名和代理配置。
5. 根据状态码判断是认证、权限、路径、限流还是上游问题。

最小验证命令：

```bash
curl -i "${BASE_URL}v1/models" \
  -H "Authorization: Bearer $YOUR_KEY"
```

---

## HTTP 状态码速查

| 状态码 | 含义 | 常见原因 | 建议处理 |
| :--- | :--- | :--- | :--- |
| **401** | 未认证 | API Key 缺失、格式错误、密钥无效或请求头未使用 Bearer 格式。 | 检查 `Authorization` 请求头，确认密钥未过期或未被管理员禁用。 |
| **403** | 无权限 | 密钥有效，但分组不允许访问该模型、渠道或端点。 | 查询 `/v1/models` 获取可用列表，联系管理员检查分组权限。 |
| **404** | 未找到 | 路径不存在、端点未启用、模型名错误或映射缺失。 | 核对端点路径，确认使用的模型名称在当前部署的可用模型中。 |
| **429** | 请求过多 | 命中网关、上游账号、分组或客户端侧的速率限制或额度封顶。 | 降低并发，使用指数退避重试，或联系管理员调整额度。 |
| **5xx** | 服务错误 | 上游服务故障、网络抖动、渠道配置错误或网关内部错误。 | 记录错误日志，稍后重试，必要时切换到备用模型或联系管理员。 |

---

## 401 未认证

> [!CAUTION]
> **401 Unauthorized**：表示请求未能通过身份验证。401 错误发生时，**通常不应在客户端发起自动重试**，应当先检查认证配置。

优先使用命令行确认 API Key 是否真的发送到了请求中：

```bash
echo "$YOUR_KEY" | wc -c
curl -i "${BASE_URL}v1/models" \
  -H "Authorization: Bearer $YOUR_KEY"
```

### 401 常见原因与处理

| 原因 | 解决方法 |
| :--- | :--- |
| **环境变量未设置** | 重新执行 `export YOUR_KEY="..."` 写入当前终端会话。 |
| **请求头缺少 Bearer** | 确保请求头格式为 `Authorization: Bearer $YOUR_KEY`。 |
| **密钥被删除或禁用** | 登录控制台或联系管理员确认该 API Key 的状态。 |
| **混淆了环境密钥** | 确保开发、测试和生产环境的 Key 对应无误。 |

---

## 403 无权限

> [!IMPORTANT]
> **403 Forbidden**：表示您的 API Key 有效，但当前绑定的**分组 (Group)** 没有访问目标模型、渠道或端点的权限。它不等于 Base URL 错误，重点在于核对权限矩阵和分组策略。

常见检查项：
1. 检查调用 `/v1/models` 是否能返回您想要请求的目标模型。
2. 当前 API Key 是否关联了正确的业务分组。
3. 该分组是否启用了目标端点及对应的分流渠道。
4. 分组的可用额度、余额或有效期是否满足此次请求的扣费预期。
5. 管理员是否近期对该分组调整过权限或费率价格。

---

## 404 未找到

> [!WARNING]
> **404 Not Found**：通常是由于客户端拼接的 URL 路径错误、调用的端点未开启、或使用了无效的模型名称。

### 404 常见检查对照表

| 检查项 | 错误示例 | 正确做法与说明 |
| :--- | :--- | :--- |
| **是否重复拼接 `/v1`** | `{{BASE_URL}}v1/v1/chat/completions` | SDK 内部会自动补全，确认 Base URL 末尾没有多余的 `/v1`。 |
| **是否缺少 `/v1beta`** | 混用原生与兼容端点路径 | Gemini 原生 API 通常需要请求 `/v1beta/models/...`。 |
| **是否需要 `/antigravity`** | 使用了标准 OpenAI 路径 | 特殊客户端或专用通道需要使用 `/antigravity` 路由前缀。 |
| **模型名是否存在** | 请求未在可用列表中的模型 | 优先请求 `${BASE_URL}v1/models` 中列出的模型名称。 |
| **端点是否启用** | 请求图像或 Embedding 但返回 404 | 确认当前部署版本是否启用了该端点能力。 |

## 模型不可用

> [!NOTE]
> 常见报错提示为：`model_not_found`、`model_not_enabled`、`no_available_channel` 或上游直接拒绝服务。

### 核心原因梳理

| 原因 | 详细说明 |
| :--- | :--- |
| **分组未开放** | 当前 API Key 所属的分组没有该模型的访问权限。 |
| **模型映射缺失** | 请求的模型名称在后台没有被映射到任何有效的实际上游模型。 |
| **渠道不可用** | 后台绑定的上游账号额度不足、Key 失效、或正处于被限流/禁用状态。 |
| **价格配置缺失** | 管理员未给该模型配置扣费费率或分组倍率，网关为防止乱扣费默认拒绝请求。 |
| **接口族不兼容** | 如使用 Anthropic 模型传递了 OpenAI 原生格式请求体，导致解析失败。 |

---

## 不支持的端点

如果接口返回 404 并带有 `unsupported endpoint` 提示，通常表明网关没有启用对应的路由，或是客户端 Base URL 拼写不正确。

| 客户端 SDK | 推荐 baseURL 设定示例 |
| :--- | :--- |
| **OpenAI SDK** | `baseURL` 通常设置为 `{{BASE_URL}}v1` |
| **Anthropic 兼容** | 请求 URL 为 `${BASE_URL}v1/messages`，防止拼接成 `${BASE_URL}v1/v1/messages` |
| **Gemini 原生** | 使用端点 `${BASE_URL}v1beta/models/{model}:generateContent` |
| **Antigravity 路由** | 使用 `${BASE_URL}antigravity/...`，且需确认部署已开启此路由组件 |

## 429 限流

> [!WARNING]
> **429 Too Many Requests**：表示客户端请求频率过快或已超出了当前时间窗口的配额限制。**强烈建议在客户端引入指数退避 (Exponential Backoff) 的重试策略，切忌进行无延迟的无限死循环重试。**

### 429 限流场景与优化方案

| 限流场景 | 优化方案建议 |
| :--- | :--- |
| **单用户高频并发** | 降低并发调用量，在客户端增加限流与排队机制。 |
| **批处理任务触发** | 分批次有序执行，限制每批的任务大小并增加执行间隔。 |
| **自动重试机制失控** | 引入带抖动 (Jitter) 的指数退避，限制最大重试次数。 |
| **上游账号被限流** | 联系管理员确认，增加备用渠道或切换分流。 |
| **分组额度耗尽** | 检查当前 API Key 额度，联系管理员调整或充值。 |

## 流式中断

> [!NOTE]
> 流式请求（Streaming）可能在生成途中断开，表现为 SSE (Server-Sent Events) 连接意外关闭、客户端超时或内容输出截断。

### 流式故障排查方向

| 可能原因 | 建议与对策 |
| :--- | :--- |
| **客户端超时过短** | 增加 HTTP Client、网关代理、反向代理和负载均衡器的超时阈值。 |
| **代理缓冲 (Buffering)** | 关闭反向代理（如 Nginx）的缓冲机制，确保 SSE 分块数据能实时转发。 |
| **上游限流或熔断** | 降低并发请求频率，检查上游账号健康状态。 |
| **网络通路不稳定** | 增加合理的重试策略（注意避免对非幂等请求盲目重放）。 |
| **模型单次输出过长** | 合理设定 `max_tokens` 参数，或将大型任务拆分为多步 Prompt 执行。 |

> [!TIP]
> 如果同一个模型的**非流式**请求调用完全正常，而**流式**请求持续报错中断，请将排查重点放在**反向代理缓冲设置**和**客户端流式解析逻辑**上。

## 最小复现与故障反馈模板

为了帮助管理员快速定位问题，请在反馈故障时提供以下脱敏后的排查信息，**请务必不要提供完整的 API Key**：

```text
反馈时间段：YYYY-MM-DD HH:MM:SS
请求路径：如 /v1/chat/completions
所用模型：如 gpt-4o-mini
HTTP 状态码：如 403
错误摘要：如 "model_not_enabled"
API Key 标识：如 "my_dev_key" 或仅提供 Key 的后 4 位
客户端类型：如 OpenAI SDK / Claude Code / curl
是否为流式：是 / 否
部署环境：本地测试 / 预发布 / 生产环境
```

### 可复现的最小 curl 脚本

```bash
curl -i "${BASE_URL}v1/chat/completions" \
  -H "Authorization: Bearer $YOUR_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [
      { "role": "user", "content": "ping" }
    ],
    "max_tokens": 20
  }'
```

> [!TIP]
> 如果上述最小 curl 请求可以成功返回，而您编写的业务代码持续失败，则说明问题通常源于**业务参数不匹配**、**上下文过长**、**多模态/流式逻辑处理不当**或**网络超时时间设置过低**。
