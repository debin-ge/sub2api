# 模型与平台

{{SITE_NAME}} 可以通过不同的中转渠道连接多个模型平台。前端或客户端应用不应假设某个部署节点一定支持全部平台、模型或端点。

> [!IMPORTANT]
> **关于可用模型**：实际可调用的模型列表，应始终以当前 API Key 调用 `/v1/models`、`/v1beta/models` 的实际返回结果或管理员提供的说明为准。

---

## 平台可用性决定因素

| 影响因素 | 核心作用与影响 |
| :--- | :--- |
| **API Key 分组** | 控制您的密钥能访问哪些特定的中转渠道、可用模型白名单以及计费倍率。 |
| **上游账号状态** | 上游供应商账号是否有效、额度是否充足、是否触发了频率限制。 |
| **模型映射 (Mapping)** | 管理员可以在后台把您请求的模型别名透明地重定向到实际上游模型。 |
| **渠道价格与倍率** | 管理员可能会根据成本策略、服务等级或优先级来开放或隐藏部分模型。 |
| **系统运行期参数** | 系统路由选择、优先级排序、禁用策略、并发限制以及频率控制等。 |

## 平台矩阵

| 平台标识 | 常见接口族 | 核心兼容性说明 |
| :--- | :--- | :--- |
| **`openai`** | `/v1/chat/completions`, `/v1/responses`, `/v1/embeddings`, 图片生成等 | 兼容标准的 OpenAI SDK 及周边生态，可用模型受渠道及后台映射限制。 |
| **`anthropic`** | `/v1/messages`, `/v1/messages/count_tokens` | 兼容 Claude Code、Anthropic SDK 或 Messages 格式的各类客户端。 |
| **`gemini`** | `/v1beta/models/*` | 兼容 Google Gemini 原生 JSON 请求体与 SSE 流式返回协议。 |
| **`antigravity`** | `/antigravity/*` | 兼容 `/antigravity` 自定义网关路由，支持聚合的 Claude 与 Gemini 风格调用。 |
| **`minimax`** | 兼容层 / 映射转发 | 适合对接 MiniMax 平台，是否开放及支持的模型取决于渠道与分组绑定。 |
| **`glm`** | 兼容层 / 映射转发 | 统一适配智谱 GLM 开放平台，支持在后台根据倍率配置调用。 |
| **`kimi`** | 兼容层 / 映射转发 | 对接月之暗面 Kimi 平台，具体上下文窗口大小以实际上游渠道为准。 |
| **`deepseek`** | OpenAI 兼容层 / 映射转发 | 适配 DeepSeek 平台，常用于主流开发辅助插件的 Chat Completions 接口中。 |
| **`windsurf`** | 客户端专属兼容入口 | 需要管理员配置特定的物理渠道、授权分组及模型映射方可使用。 |
| **`opencode`** | `/v1/responses` / 兼容入口 | 专为接入 OpenCode2API 及各类支持 Responses API / OpenAI 风格的 Coding CLI 设计。 |

## 如何确认模型可用

在正式配置代码或客户端前，推荐先在终端中发起以下验证请求：

```bash
# OpenAI/Claude 风格模型查询
curl "${BASE_URL}v1/models" \
  -H "Authorization: Bearer $YOUR_KEY"
```

如果您打算使用 Gemini 原生的 SDK，可以请求以下端点：

```bash
# Gemini 风格模型查询
curl "${BASE_URL}v1beta/models" \
  -H "Authorization: Bearer $YOUR_KEY"
```

> [!WARNING]
> **提示**：**请不要把文档中的示例模型名当成保证可用的模型。** 示例模型名仅用于演示入参格式。在生产开发中，应始终以接口实际返回的可用列表或管理员指定的模型名称为准。

## 模型选择策略建议

在配置系统时，建议基于具体场景的任务目标来理性选择模型，而非盲目追求最新或最热的模型：

| 任务类型 | 模型选择建议 | 关注的评价指标 |
| :--- | :--- | :--- |
| **分类、打标、简单格式化** | 优先选用低成本、低延迟的轻量级模型。 | 单次请求成本、可用率、高吞吐。 |
| **常规客服问答、自然对话** | 选择首字延迟低、回答风格稳定的通用聊天模型。 | 首字响应延迟 (TTFT)、推理质量。 |
| **长文档总结、RAG 检索** | 选择支持超长上下文 (Long Context) 且有良好针寻率的模型。 | 上下文窗口、知识检索相关度。 |
| **复杂逻辑推理、算法规划** | 优先选用推理型模型 (Reasoning Model)，并限制单次输出上限。 | 推理准确率、输出指令一致性。 |
| **代码生成、代码审查 (CLI)** | 优先使用针对代码工作流优化、支持 Responses 或 Tool Call 的模型。 | 代码语法正确性、多文件上下文处理能力。 |
| **文本向量化 (Embedding)** | 必须使用专用的 Embedding 模型，切勿使用普通 Chat 模型替代。 | 向量相似度、多语言嵌入效果、成本。 |
| **图片生成与编辑** | 根据上游平台能力，调用专属的 Image 生成端点。 | 画面质量、生成速度、分辨率参数。 |

## 端点与模型匹配

> [!IMPORTANT]
> **端点与格式匹配**：在网关接入中，即使您的 API Key 拥有某模型的权限，如果请求体格式与访问端点不匹配，调用依然会失败。

| 模型/客户端类型 | 目标调用端点 | 请求体与协议规范 |
| :--- | :--- | :--- |
| **OpenAI 兼容模型** | `/v1/chat/completions` | 请求体必须为标准的 `messages` 数组。 |
| **Responses 兼容模型** | `/v1/responses` | 适合 Codex CLI 等支持 OpenAI Responses 协议的开发客户端。 |
| **Claude / Anthropic 兼容模型** | `/v1/messages` | 请求体通常必须显式指定 `max_tokens` 参数。 |
| **Gemini 原生模型** | `/v1beta/models/{model}:generateContent` | 请求体必须遵循 `contents` 与 `parts` 的嵌套格式。 |
| **Embedding 文本向量模型** | `/v1/embeddings` | 输入数据应为文本字符串或文本数组。 |

## 生产上线前验证

将项目接入生产环境前，建议按照以下步骤进行彻底验证：
1. 使用您的生产 API Key 调用 `/v1/models`。
2. 用生产环境相同的 Base URL 发起最小非流式请求。
3. 如果业务涉及打字机流式效果，还需验证流式 (SSE) 请求。
4. 使用真实的业务提示词 (Prompt) 样本进行上线前的小规模基准测试。
5. 确认管理员在后台针对该分组配置了自动容灾备用渠道。
6. 在客户端代码中保留模型名和端点 URL 的热重载或快速回滚配置。

## 常见错误排查

| 异常现象 | 潜在原因分析 |
| :--- | :--- |
| **`/v1/models` 响应空列表** | API Key 分组内未授权任何模型，或后台渠道全部下线。 |
| **接口调用返回 404** | 路径拼写错误、网关子路由未启用或客户端协议与端点不兼容。 |
| **接口调用返回 403** | 密钥验证通过，但该 Key 归属的分组无权调用指定模型。 |
| **上游平台报错透传** | 上游 API 欠费、被封禁、触发区域風控或请求参数包含非法字段。 |
| **流式 (SSE) 中途断连** | 代理服务器超时、网络抖动或上游反爬机制导致的连接截断。 |

## 备用模型降级策略

对于高可用（HA）要求极高的生产业务，建议在客户端代码中实现多模型热切，以防止单一供应商通道故障：

| 降级策略 | 适用场景 | 运作方式 |
| :--- | :--- | :--- |
| **同规格平替** | 接口格式与能力相近的模型，作为第一备选。 | 捕获 429 或 5xx 后，使用原参数名切换到平替模型重试。 |
| **降级到轻量** | 复杂推理不可用时，使用轻量模型重试。 | 牺牲一定的推理深度，使用轻量模型优先保障业务可用性。 |
| **队列与重试** | 异步或离线任务。 | 配合退避算法重试，避免在故障期持续重试产生请求雪崩。 |
