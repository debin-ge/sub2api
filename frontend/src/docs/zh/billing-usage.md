# 计费与用量

{{SITE_NAME}} 的计费和用量展示取决于当前部署的分组、渠道价格倍率、额度参数和管理员设定的扣费策略。由于不同部署采用的收费逻辑差异较大，本页仅说明您在接入和对账时应当了解的通用核心原则。

---

## 用量通常如何产生

| 用量产生项 | 详细说明 |
| :--- | :--- |
| **输入 Token (Prompt)** | 包含发送给模型的系统提示词 (System Prompt)、历史对话上下文、用户当前输入以及工具定义等。 |
| **输出 Token (Completion)** | 模型推理生成的回复文本、生成的工具调用参数或结构化 JSON。 |
| **图像/多模态能力** | 图像生成、编辑或视觉输入等操作，通常按单张图片分辨率、数量或上游单价计费。 |
| **文本向量 (Embedding)** | 通常按输入文本的 Token 数量或 API 调用请求次数独立计费。 |
| **重试请求** | 客户端在失败或超时后发起的自动重试，会被中转网关视作新的独立请求，从而产生多次计费。 |

> [!NOTE]
> **关于流式请求计费**：流式输出（SSE 打字机效果）仅改变了服务器向客户端返回数据的方式，**并不代表免费或价格更便宜**。只要上游模型生成并向网关返回了内容，即使中途断开，已生成的 Token 仍然会被计入您的账单用量。

---

## 影响用量单价的维度

| 维度 | 影响方式 |
| :--- | :--- |
| **模型版本** | 不同性能的模型单价存在巨大阶梯差异（输入与输出价格通常不同）。 |
| **所属分组** | 管理员会为不同的用户、环境或开发小组设置不同的渠道权重、价格加成和初始额度。 |
| **分流渠道** | 即使是同一个模型，后台通过不同账号分发，其实际成本和可用性也会有所不同。 |
| **模型映射** | 请求被映射到具有不同费率的更高/更低级实际上游模型时，会影响最终扣费。 |
| **请求参数** | `max_tokens` 设定、批量 (batch) 输入的厚度、以及图像的分辨率级别等。 |

> [!IMPORTANT]
> **对账凭据**：如果您在扣费方面有任何疑问，请登录当前部署的控制台查询详细账单明细，或直接以管理员提供的具体费率规则为准。

## 请求前估算成本

在业务上线前，建议您使用以下做法来减少计费的不确定性：
1. 先评估任务难度，优先选择性价比较高的轻量级模型。
2. 精简历史对话，只把核心上下文发送给模型，减少输入 token 的冗余。
3. 在代码中强制限制 `max_tokens`，防止模型由于跑偏而生成超长的无用回复。
4. 对长文档处理，建议采用先在本地截断、提取摘要或分段处理的策略。
5. 上线前用真实业务提示词发起几组测试，根据后台账单记录测算平均请求开销。

> [!TIP]
> 如果您连接的 Anthropic 兼容端点支持 Token 预估功能，可以请求下述端点获取估算值：
>
> ```bash
> curl "${BASE_URL}v1/messages/count_tokens" \
>   -H "Authorization: Bearer $YOUR_KEY" \
>   -H "Content-Type: application/json" \
>   -d '{
>     "model": "claude-3-5-sonnet-latest",
>     "messages": [
>       { "role": "user", "content": "请估算这段请求的 token。" }
>     ]
>   }'
> ```

## 查看消费用量

通常情况下，平台控制台会提供用量总览与账单明细页面，您可实时跟踪以下指标：

| 核心字段 | 指标具体含义 |
| :--- | :--- |
| **时间 (Time)** | 请求发生的精确时间戳或统计计算窗口。 |
| **模型 (Model)** | 用户请求发送的模型名，以及网关实际中转的底层模型名。 |
| **输入/输出 Token** | 单词请求所耗费的具体 Prompt Tokens 与 Completion Tokens 数量。 |
| **调用状态 (Status)** | 显示请求是否成功，或因余额不足、上游报错、并发限制等导致的阻断状态。 |
| **费用 (Cost)** | 根据分组费率和渠道规则折算后的真实扣费额度。 |

## 对账与异常用量排查

> [!WARNING]
> **安全警示**：当您发现账户额度消耗速度异常，在联系管理员或提交工单进行对账时，**请绝对不要将包含完整 API Key 的截图或明文发送出去**。

请提供以下脱敏后的排查线索：
1. 消费出现异常的精确时间段。
2. API Key 的名称，或仅展示其最后 4 位字符。
3. 产生高频调用的接口路径及模型名称。
4. 客户端或微服务部署的环境名。
5. 错误日志中记录的报错码和并发情况。
6. 近期是否上线了包含自动轮询、自动重试或循环触发的业务逻辑。

## 账户预算与安全建议

对于生产环境系统，推荐在接入前完成以下配置：

| 安全措施 | 具体操作建议 |
| :--- | :--- |
| **多环境密钥隔离** | 测试、预发、生产环境严格使用不同的 API Key。 |
| **限额封顶** | 在控制台为特定的 API Key 或分组设置每日/每月的限额封顶。 |
| **阈值告警** | 开启余额不足或额度消耗过快的主动告警通知。 |
| **模型访问白名单** | 仅为 Key 开启业务必须使用的模型，防止意外误用高价模型。 |
| **上线监控** | 新功能发布后，在控制台对请求频次和消费曲线进行 30~60 分钟的连续观察。 |
