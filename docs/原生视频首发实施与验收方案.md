# 原生视频首发实施与验收方案

> 范围更新：2026-09-06。用户已要求开放编辑、延长、角色和回调，并兼容 Seedance 2.0 扁平参数与火山 `content[]`。本文件的待执行步骤不是生产操作或收费调用授权。
> 生产尚未应用本次视频迁移。Grok 不属于此次新增交付或待办；项目原有 Grok 功能保留。
> 实施更新（2026-09-06）：P1-P6 的本地工具、文档和隔离验证已推进，最新结果见第 6 节。真实收费、生产发布、目标环境回滚及真实容量/告警接收尚未执行。

## 1. 首发边界

开放候选：OpenAI API Key、标准余额计费、视频创建/编辑/延长、角色创建/查询/删除与复用、幂等重放、列表、查询、下载、删除、客户端回调及上游 webhook。实际模型、价格和账户仍需在发布环境确认；本文件不声明真实收费调用已经完成。

客户端回调保持配置级 opt-in：默认关闭，开启时必须配置签名密钥；上游 webhook 仍要求账户级签名密钥。非法派生、超过 6 次或 120 秒的延长、跨账户角色、私网 callback URL 和不合法 Seedance 参数必须在任务/hold/上游提交前拒绝。

不删除底层 Provider adapter、资源状态机、结算/删除恢复或数据库对象。它们不构成公开入口，保留其安全测试；不为未发布的本地数据新增接管、迁移或更正系统。不执行现有开发库清空。

## 2. 已落地的首发限制

- HTTP、原生 Submit 和创建意图入口统一允许已发布操作；未知操作仍由发布策略拒绝。
- JSON 与 multipart 编辑、延长、角色和 `characters` 已接入原子 task/hold、幂等、账户亲和、结算和删除恢复链。
- 客户端回调默认配置仍为关闭；开启后启动耐久投递 Worker，管理员可重试未过期失败；入站 webhook 验证签名后只唤醒原任务，不直接改写终态。
- Seedance 2.0 扁平字段与 `content[]` 归一到同一请求 DTO；严格拒绝未知字段、重复键、冲突来源和非法素材组合。

## 3. 其余必需项的实施方案

下列是各工作包的范围与验收标准，实际完成状态以第 6 节为准。不通过追加非首发功能来代替验收。

### P1. 当前运行手册和发布配置

工作：以本次边界维护可执行视频运行手册；列出模型/价格、上游账户、总开关与创建开关、加密密钥、下载代理、轮询 Worker，以及可选 callback Worker 的必要配置。

交付：一份基础流程运行手册、一份配置核对表；同步收口清单，标明哪些操作需人工授权。

验收：从干净配置启动隔离实例，关闭总开关时不开放 API；回调关闭时基础及派生操作仍可用，带 `callback_url` 的请求明确返回 403；开启回调时签名、投递和管理重试可验证。

### P2. 真实上游最小闭环

工作：准备一个显式手动运行的 smoke 脚本，接收测试服务地址、测试用户 Key 和允许的模型；凭据只从环境或受控输入读取，不进入源码、日志或报告。设置明确调用次数及预算，脚本不自动重试新建请求。

场景：一次创建、同 key 同 body 重放、同 key 不同 body 冲突、查询至终态、下载、删除及重复删除；使用第二个用户验证任务/内容不可访问。核对 task、hold、capture/release、usage、余额变化只发生应有的一次。

交付：脱敏结果表和请求 ID，区分协议结果与账务证据。真实调用前必须由用户确认账户、模型、费用上限和环境；未经授权不执行。失败只修复有反例的基础流程缺陷。

### P3. 基础恢复和授权故障验证

工作：复用现有 mock Provider、隔离 PostgreSQL/Redis 和 Worker，增加有界的进程级场景，不建设新的故障平台。

场景：提交结果不确定后不自动再次 Create；提交成功本地落库前退出后保持隔离；结算提交后、确认前退出不双扣；删除失败或进程重启后可恢复；Redis 不可用时数据库恢复仍推进；用户/分组/账户权限变化不得跨用户披露内容。

交付：每个场景的初始状态、故障点、恢复后的任务与资金断言。计划多实例部署时，再增加租约过期接管和旧领取者写入拒绝的真实多进程验证；启用回调的环境同时覆盖租约续期、重试、隔离和过期窗口。

### P4. 浏览器基础流程验收

工作：在隔离环境用桌面和移动视口检查实际存在的任务/管理页面，覆盖加载、空列表、分页、刷新、详情切换、错误、待结算、删除中、重复点击和权限拒绝。

交付：最小浏览器回归及截图。只验证当前产品已有界面，不为验收新增创作工作台；API-only 流程由 P2 验证。Callback 队列对失败/隔离且未过期的投递展示防重复重试操作。

### P5. 首次迁移、切换和回滚演练

工作：在与目标数据库版本相符、且从生产现有迁移基线构建的隔离环境演练新增 238-254、264、265_video_failed_auto_release.sql 与 266_video_task_provider_url.sql；后两项为原生视频迁移，与已删除的同编号 Grok SQL 不同。验证既有表数据及 Grok 原有链路不受影响。沿用当前迁移执行器，不跳过 checksum、不重排编号、不新增退役或兼容迁移。迁移 240 的列类型调整需要 `breaking-migration` 标签，本次按停机发布执行；提交前门禁使用 `--worktree` 覆盖未跟踪文件。

发布顺序：确认备份和恢复方式；选择维护窗口并停止旧实例写入；执行迁移、部署统一版本；先不开创建做健康检查；受控 smoke 通过后再按批准范围开放创建。

回滚边界：放流前失败可保持关闭并恢复经验证的版本/备份；已经产生真实任务后，先停止新建并保留能处理新 task/outbox 的恢复实例，不直接回滚数据库或让旧版本接管新义务。

交付：可执行的发布/回滚步骤及演练结果。目标环境、备份、维护窗口和实际生产 DDL 均另行确认；首次上线不自动扩大成历史视频接管工程。

### P6. 最小监控与容量验证

工作：复用已有指标和告警，确认 poll、settlement、delete、callback/outbox 的积压数量/最老时间、Worker 错误、数据库连接与锁等待可见；回调关闭时不应产生误导性告警，开启时必须监控重试和隔离积压。

用约定的小规模并发执行有界测试，观察预算查询、账户并发、连接池和内容代理；修复已测出的瓶颈，不先做全系统预算重构或大规模压测平台。

交付：约定负载、运行结果、告警触发与恢复证据。阈值根据目标环境确认，不凭空承诺容量或延迟。

## 4. 顺序与停止条件

1. 先完成 P1、P3 和 P4 的本地/隔离部分，P6 做基础观测接线。
2. 用户确认真实测试账户、模型和预算后执行 P2；确认部署拓扑后补齐对应 P3 场景。
3. 在目标版本的隔离数据库完成 P5 和约定负载下的 P6。
4. 仅在全部首发必需项有证据、已知阻塞缺陷关闭、生产操作获授权后发布。

停止条件：创建/编辑/延长/角色/资源访问/删除/计费/恢复闭环通过，配置级回调边界与 webhook 签名可验证，发布与观测证据齐全。可信上传视频计量、自动身份验真、全系统 reservation、Grok 兼容/迁移/更正不作为完成条件。
