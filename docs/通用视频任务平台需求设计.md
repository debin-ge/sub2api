> 历史账务更正执行需求补充（2026-09-06）：approved plan 必须通过独立 apply command 执行，执行人是不同于提出人的当前 active admin，并提交个人 actor、当前 job version、稳定 operation key 和 reason。数据库必须在同一事务创建不可变 execution/逐维 adjustment/correction usage audit，CAS 更新当前余额与 subscription/Key/账户/平台 quota，绑定 job execution 后进入 `billed`，同时创建持久化缓存投影义务。原 usage、dedup 和 effect archive 不得更新；过期 rate window 只记录零实际增量。

> 历史账务更正计划需求补充（2026-09-06，历史阶段）：`safe=true` preview 可以冻结为不可变 correction proposal，并由另一名 active admin approve/reject。proposal 必须绑定数据库计算的 preview hash、archive identity、job version 和 source facts；普通 Grok billing review 与 correction review 不得同时 pending。批准仅形成执行授权且自身无资金副作用；后续执行只能遵循上方独立 apply 需求。

> 历史账务更正预览需求补充（2026-09-05）：拥有 migration 267 精确 effect archive 的 legacy Grok mismatch，管理详情必须只读展示实际 command/usage 与冻结应有 effect/usage、逐维金额差额和 fail-closed blocker。archive 缺失、payload 不支持、usage facts 冲突、账户 quota 策略无法证明或 subscription→balance 的历史平台 quota 策略未知时，`safe=false`。本批禁止任何 apply API、按钮或资金副作用。

> 账务副作用证据归档需求补充（2026-09-05）：migration 267 要求任何 durable billing outbox 一旦实际应用账务或执行 legacy projection repair，就在同一事务把精确 command/result 与最小 usage facts 写入不可变 effect archive，之后才允许删除 outbox。普通幂等无副作用重放不重复归档；已被历史版本确认并删除的 outbox 无法反推，仍不得凭 usage 行猜测多维 quota 副作用。该批是历史更正账本的前置证据层，不执行任何退款、补扣或 quota 调整。

> legacy 提升与账务结论需求补充（2026-09-05）：migration 265 只允许经过双人不可变审批和冻结账号精确 Provider GET，将可验证的 legacy Grok 归档候选提升为 synthetic intent 与 durable job；提升结果固定进入 `manual_review`，绝不自动生成 usage、outbox 或资金变化。migration 266 再用独立双人账务复核区分“无任何 usage/dedup 时按冻结事实重试”“既有 usage 与全部冻结事实精确一致时确认”及“免单”；存在不匹配证据时禁止重试或确认，等待历史更正账本。

> multipart 创建意图需求补充（2026-09-05）：原生 OpenAI 与 Composite managed multipart 必须先把文件流写入加密 spool，再以字段名、文件名、规范 MIME、长度和 SHA-256 形成 `canonical_multipart_v1`，并在路由、预算、hold 与 Provider Submit 前领取共享 `video_create_intents`。同 key 的 JSON/multipart 合同变化或 multipart 内容变化必须冲突；原生任务一旦绑定，后续 Composite 路由变化只能重放原任务。Composite 命中 Grok 时只允许从加密 spool 流式重建 multipart，不新增明文落盘。

> Provider identity 需求补充（2026-09-05）：`verified` 不能再是可编辑布尔状态，必须由当前 identity version 的持久 principal binding 支撑，并经过两个不同 active admin 的不可变审批。数据库只保存规范化 origin/principal hash，已知 shared/cross-owner alias 阻断验证与调度，紧急撤销级联所有已登记 alias。人工 evidence 仍不等于 Provider 侧自动证明，外部真实性和 alias 全集继续作为发布门禁。

> legacy 归档阶段说明（2026-09-05）：migration 263 先以有界扫描归档无 key Grok Redis 作业的脱敏证据，数据库接管可验证账号亲和，并永久阻断旧 Redis 自动计费；263 本身不会自动提升或按当前账号/价格补扣。后续 migration 265/266 已增加人工证据驱动的双人提升和账务结论，仍不把当前 principal 当作自动创建期证明。

> 首次意图合同补充（2026-09-05）：同 owner、endpoint、规范 Idempotency-Key 的视频创建不能因 alias/Provider 切换而重复提交。相同请求重放先于生成预算/RPM，仍须有效身份与访问授权；未知结果不自动重建。受支持 JSON、legacy Grok multipart、原生 OpenAI multipart 与 Composite managed multipart 均已接入共享意图；这仍不代表 legacy Grok 已完成原生 hold/outbox 迁移或生产混版本验收。

> 时间契约补充（2026-09-05）：新视频任务按实际资金结算事务入账时间更新 Key/平台预算，生成终态观察时间单独保留。入账回执与金额原子持久化，重试不重复消费；不是按历史生成时间释放当前预留而不记当前费用。详见修复方案 4.3.1 与修复实施记录第 8 节。

> 安全修复说明（2026-09-05）：本文保留原需求基线；与《通用视频任务平台安全业务逻辑修复方案》冲突时，以修复方案为准。独享账户必须全局隔离，不能仅用 `video_owner_user_id` 授予长期密钥访问；未验证的上游身份一律不披露长期凭据。实施与验收进度见《通用视频任务平台修复实施记录》，原需求条目不代表已经完成安全验收。

## 0. 执行摘要

本设计将视频能力建设为独立的长期平台能力，而不是继续扩展现有 Grok 视频转发分支。系统以本地 `video_tasks` 为任务、权限、状态和计费的唯一事实来源，通过 `VideoProvider` 适配 OpenAI、Grok、火山等不同供应商。

首版必须支持：

- OpenAI 风格的视频创建、查询、列表、删除和内容下载接口。
- 参考图、参考视频及 Provider 支持的其他二进制输入。
- Provider 入站 webhook、平台轮询和用户出站 callback。
- 标准余额预占、终态结算、退款和异常隔离。
- 平台生成的公开任务 ID，以及受策略控制的 Provider 信息、上游任务 ID和访问凭证暴露。
- 下载时从原 Provider 流式代理 video、thumbnail、spritesheet 等内容变体。

平台不建设永久资产托管能力：

- 不增加 `AssetStore`。
- 不增加 `video_assets` 表。
- 不永久保存输入或输出媒体。
- 不把视频复制到 S3、OSS、本地归档目录或 CDN。
- 二进制输入只允许进入加密的短期 `SubmissionSpool`，上游确认接收后立即删除。
- 下载响应只在请求期间流经进程，不缓存、不落盘。

## 2. 目标与非目标

### 2.1 目标

1. 为所有视频 Provider 提供统一的任务生命周期、账户亲和、并发、计费和审计模型。
2. 对 OpenAI Videos 提供完整的核心闭环，包括二进制输入和内容下载。
3. 在进程崩溃、Redis 丢队列、webhook 重复或乱序、结算重试时保持任务和资金一致。
4. 防止创建响应丢失造成重复生成、重复成本或错误退款。
5. 允许未来通过可选能力接口增加 edit、extend、character、cancel 和任务搜索，而不修改基础 Provider 契约。
6. 保持现有 Batch Image 和 Grok 的 request ID、预占及计费行为不变。

### 2.2 非目标

- 不提供平台级视频长期保存、图库、CDN、转码、转封装、缩略图生成或内容分发。
- 不对媒体内容建立可复用资产 ID。
- 不在首版实现订阅额度 reservation。
- 不用 Provider 列表接口作为用户任务列表的事实来源。
- 不通过创建时间、prompt hash 或模型相似度猜测关联 `submission_unknown` 任务。
- 不保证 Provider 自身内容过期、账号失效或上游删除后的可下载性。

## 3. 总体架构

```text
OpenAI /v1/videos       Grok/Volcengine Native       Future Canonical API
        |                         |                           |
        +---------------- Protocol Adapters -----------------+
                                  |
                         VideoTaskService
                 create/get/list/delete/content
                                  |
        +-------------------------+-------------------------+
        |                         |                         |
 VideoProvider Registry   Reservation/Settlement    SubmissionSpool
        |                         |                  (temporary only)
 OpenAI/Grok/Volcengine     hold/outbox/usage                |
        |                         |                         |
        +---------------- PostgreSQL -----------------------+
                                  |
                     Redis queues + background workers
                                  |
             poll / webhook / settlement / callback / sweep
```

依赖方向必须保持：

- Protocol Adapter 依赖视频领域服务。
- 视频领域服务依赖 Provider、Repository、Billing 和 Spool 接口。
- Provider 只处理上游协议，不依赖 Gin、用户余额、数据库模型或公开响应格式。
- Billing 不依赖具体 Provider。
- Repository 不解析 OpenAI、Grok 或火山协议字段。

## 4. 公共 API

### 4.1 OpenAI 兼容入口

首版注册：

| 方法 | 路径 | 行为 |
|---|---|---|
| `POST` | `/v1/videos` | 创建视频任务，支持 multipart 二进制输入 |
| `GET` | `/v1/videos/{video_id}` | 查询本地任务及最新上游状态 |
| `GET` | `/v1/videos` | 查询当前用户的本地任务列表 |
| `GET` / `HEAD` | `/v1/videos/{video_id}/content` | 流式代理结果或指定 variant |
| `DELETE` | `/v1/videos/{video_id}` | 删除或取消上游任务并保留本地审计 |

`video_id` 始终是平台生成的公开 ID。即使响应中暴露了 `provider_task_id`，公共查询、删除和下载路由也不接受它替代本地 ID。

首版 `POST /v1/videos` 支持 OpenAI 官方字段，并允许协议适配器根据 Provider capability 接收扩展输入。至少包括：

- `model`
- `prompt`
- `seconds`
- `size`
- `input_reference`
- 用户 callback 扩展字段 `callback_url`

未知字段的处理遵循对应协议：OpenAI 入口默认严格校验；Provider 原生入口可保留安全的未知字段透传，但计费相关字段必须先结构化解析。

自定义 OpenAI-compatible 视频上游可显式接收 `ratio` / `aspect_ratio`、`image_url`、`first_image_url`、`last_image_url`、`reference_images`、`reference_videos` 和 `reference_audios`。这些字段必须结构化校验后转发，不能通过自由 `provider_options` 绕过数量、组合、URL 和计费输入类型校验；官方 `api.openai.com` 仍只接受官方字段。

JSON `input_reference.file_id` 不能仅凭调用方提供的上游文件 ID 直接使用。由于本平台不建设 `AssetStore`、也没有通用上游文件所有权表，首版只允许当前用户独享/BYOK 账户使用 `file_id`，并把该账户固定为任务账户；共享账户池不得接受 `file_id`。`image_url` 和本次请求上传的图片仍按普通账户调度与安全校验处理。

### 4.2 幂等

- 创建接口接受 `Idempotency-Key`。
- 幂等范围为 `user_id + endpoint + idempotency_key`，不绑定 API key，避免 key 轮换破坏重放。
- 平台对规范化标量字段、输入 part 元数据及媒体 SHA-256 计算稳定 `request_hash`。
- 相同 key 和相同 hash 返回原任务。
- 相同 key 和不同 hash 返回 HTTP 409，错误码 `video_idempotency_conflict`。
- 调用 Provider 时使用稳定的本地任务 ID作为 client token；Provider 支持原生幂等键时必须传递。

### 4.3 响应扩展

标准任务对象可以增加以下 sub2api 扩展字段：

```json
{
  "id": "video_01J...",
  "status": "queued",
  "provider": "openai",
  "provider_task_id": "video_upstream_...",
  "provider_access": {
    "kind": "signed_url",
    "value": "...",
    "scope": "video_content",
    "expires_at": 1788000000
  }
}
```

扩展字段由暴露策略过滤。包含任何凭证的响应必须设置 `Cache-Control: private, no-store`，并禁止写入访问日志、审计 body、错误追踪和指标 label。

### 4.4 状态投影

内部状态不得直接作为 OpenAI 状态返回：

| 内部状态 | OpenAI 投影 |
|---|---|
| `preparing`、`held`、`submitting`、`submission_unknown` | `queued` |
| `queued` | `queued` |
| `in_progress` | `in_progress` |
| `completed` 且已结算 | `completed` |
| `failed`、`cancelled`、`expired` | `failed`，并给出稳定错误对象 |

生成已完成但结算仍为 `capture_pending` 时，不得对用户暴露可下载成功态。GET 可先触发一次幂等结算；仍未成功时返回可重试错误 `video_settlement_pending`。

## 5. VideoProvider 契约

### 5.1 基础接口

```go
type VideoProvider interface {
    Name() string
    Capabilities() VideoCapabilities
    SupportsAccount(account *Account) bool

    Create(
        ctx context.Context,
        account *Account,
        request VideoCreateRequest,
        inputs []VideoInput,
    ) (*ProviderVideoTask, error)

    Get(
        ctx context.Context,
        account *Account,
        ref ProviderTaskRef,
    ) (*ProviderVideoTask, error)

    OpenContent(
        ctx context.Context,
        account *Account,
        request ProviderContentRequest,
    ) (*ProviderContent, error)

    Delete(
        ctx context.Context,
        account *Account,
        ref ProviderTaskRef,
    ) error
}
```

基础接口只包含创建、查询、内容读取和删除。用户列表读取本地 `video_tasks`，因此 `List` 不能放入基础接口。

### 5.2 可选能力

以下能力使用独立接口和 capability：

- `VideoCanceller`
- `VideoEditor`
- `VideoExtender`
- `VideoCharacterProvider`
- `VideoTaskSearcher`
- `VideoWebhookVerifier`
- `VideoAccessRefresher`
- `VideoCapabilityProber`

调用前必须检查 capability。Provider 不支持时返回统一的 `video_capability_unsupported`，不能依靠空实现或上游 404 判断。

OpenAI 官方 API-key 账户的视频能力必须采用 fail-closed 发现机制：

- `VideoCapabilityProber` 使用不创建任务、不产生生成费用的 `GET /v1/videos?limit=1` 探测，结果规范化为 `supported`、`unsupported` 或 `unknown`。
- 只在 `accounts.extra.video_capability_probe` 保存 Provider、capability、状态、检查时间、HTTP 状态和有界错误摘要；不得保存 API key、请求/响应正文、URL 或响应 header。
- 官方 `api.openai.com` 账户没有显式 override 时，只有最近一次探测为 `supported` 才能进入视频调度；`unsupported` 和 `unknown` 均拒绝调度。
- 账户创建或身份字段更新后异步触发探测；后台按有界分页周期刷新。稳定结果最多缓存 6 小时，`unknown` 最多缓存 5 分钟。
- API key、Base URL、代理、User-Agent 或 header override 变化时清除旧探测结果，防止把旧身份结论复用到新身份。
- 自定义 Base URL 不因探测可达而自动获得视频能力，必须通过 `openai_capabilities` 显式声明；Azure、OAuth 和 SetupToken 首版不参与 OpenAI Videos 调度。
- `video_capability_probe` 是平台受管字段，普通账户创建、编辑和批量 extra 更新不得伪造或覆盖。

### 5.3 规范化 DTO

`VideoCreateRequest` 至少包含：

- 本地任务 ID和稳定 client token
- operation 和 parent task
- requested/public/channel/upstream model 映射链
- prompt
- duration seconds
- width、height 和原始 size
- quality、service tier、audio 等通用属性
- Provider 扩展字段的结构化 map

`VideoInput` 至少包含：

```go
type VideoInput struct {
    Role      VideoInputRole
    FileName  string
    MIMEType  string
    Size      int64
    SHA256    string
    Open      func(context.Context) (io.ReadCloser, error)
}
```

`VideoInput` 不暴露本地路径。`Open` 只在 submission spool 有效期内可用，Provider 必须在 `Create` 返回前关闭所有 reader。

`ProviderContentRequest` 包含本地任务引用、上游任务引用、variant、Range 和条件请求头。`ProviderContent` 包含 HTTP 状态、受控响应头和 `io.ReadCloser`，不得包含已经缓冲的完整媒体字节。

### 5.4 Provider 错误

Provider 错误至少包含：

- `kind`：validation、authentication、permission、quota、rate_limit、not_found、conflict、upstream、transport。
- `retryable`：是否允许查询或控制类操作自动重试。
- `submission_certainty`：`rejected`、`accepted`、`unknown`。
- `provider_code` 和经过脱敏的 message。
- 可选的 `retry_after`。

创建调用的网络超时、连接复位或响应解析失败不能自动解释为 `rejected`。只有可以证明上游未创建任务时才能释放预占并自动重试。

## 6. 二进制输入与 SubmissionSpool

### 6.1 为什么需要短期暂存

multipart 标准不保证标量字段和文件 part 的顺序。平台必须在调用 Provider 前完成模型解析、账户选择、计价和余额预占，因此无法对任意合法 multipart 请求进行完全无缓冲的直接转发。

`SubmissionSpool` 是请求提交基础设施，不是资产系统：

- 没有公共 ID和业务查询接口。
- 不进入 `video_assets` 或其他资产表。
- 不在任务完成后保留。
- 不用于结果下载、复用、图库或 CDN。
- 不承诺跨实例和跨进程恢复。

### 6.2 写入要求

- 使用 `multipart.Reader` 顺序读取，禁止调用可能自动写系统临时目录的默认 `ParseMultipartForm`。
- 标量字段使用严格大小上限；媒体 part 直接流式写加密 spool。
- 每个 part 使用随机数据密钥和随机 nonce，加密文件名不可推导用户或任务信息。
- 写入过程中计算 SHA-256、字节数并执行 MIME sniff；客户端 MIME 只能作为提示。
- 单 part、单请求和用户并发 spool 上限来自配置及 Provider capability，超限立即中止。
- `input_reference` 图片同时受现有内容审核的 8 MiB 单图上限约束；模型目录不得为该 role 配置更大的上限。
- 对压缩包、路径名、控制字符、重复关键字段和未知媒体 role 做明确校验。
- spool 目录必须是专用目录，不得使用仓库目录、日志目录或系统共享上传目录。

参考图审核必须发生在创建任务、冻结余额和调用 Provider 之前。JSON `input_reference.image_url` 直接进入既有图片审核输入；multipart 参考图从加密 spool 打开 reader，以有界流构造审核用 data URL，读取超过 8 MiB 时立即拒绝。审核请求及其审计记录不得持久化原始图片、data URL 或 spool 定位信息；审核拒绝或不可用时不得留下任务、hold 或 Provider Submit。

### 6.3 生命周期

```text
receive multipart
    -> encrypted spool + request hash
    -> validate + reference-image moderation
    -> resolve pricing/account
    -> create task + hold
    -> mark submitting
    -> Provider.Create reads decrypted streams
    -> provider result persisted
    -> close readers and delete spool
```

- 请求在完成接收前断开：删除 spool，不创建任务，不冻结余额。
- 创建任务后、调用上游前失败：记录明确失败并释放预占。
- 开始上游调用后进程或网络结果不明：任务进入 `submission_unknown`，不自动释放。
- 正常返回、明确拒绝或未知结果都必须执行删除；删除失败进入安全告警和 sweeper。
- sweeper 根据文件创建时间清理超过 TTL 的孤儿，不能依赖数据库任务状态决定是否保留。

为了保持一致语义，首版纯文本和带文件请求都采用“同步提交、异步生成”：HTTP 创建请求等待 Provider 返回任务接收结果，后台 worker 只负责后续查询、状态收敛和结算。

## 7. 数据模型

### 7.1 video_tasks

建议字段分组如下：

| 分组 | 字段 |
|---|---|
| 身份 | `id`、`public_id`、`user_id`、`api_key_id`、`group_id` |
| 路由 | `provider`、`channel_id`、`account_id`、`account_owner_user_id` |
| 模型 | `requested_model`、`public_model`、`channel_model`、`upstream_model` |
| 关系 | `operation`、`parent_task_id`、`root_task_id` |
| 请求 | `request_hash`、`idempotency_key`、`input_manifest`、规范化计费维度 |
| 上游 | `provider_task_id`、`provider_status`、`provider_created_at` |
| 状态 | `generation_state`、`billing_state`、`delete_state`、`version` |
| 结果 | `progress`、`usage_snapshot`、`response_metadata`、`content_variants`、`content_expires_at` |
| 凭证 | `provider_access_kind`、`provider_access_enc`、`provider_access_expires_at` |
| 计费 | `billing_unit`、`estimated_units`、`actual_units`、`price_snapshot`、`hold_id`、`hold_amount`、`actual_cost` |
| 调度 | `next_action_at`、`poll_attempts`、`lease_owner`、`lease_expires_at` |
| 错误 | `last_error_kind`、`last_error_code`、`last_error_message` |
| 时间 | created/submitted/finished/settled/deleted/quarantined timestamps |

约束与索引：

- `public_id` 全局唯一。
- `(provider, account_id, provider_task_id)` 在上游 ID非空时唯一。
- `(user_id, endpoint, idempotency_key)` 在幂等键非空时唯一。
- owner 列表索引使用 `(user_id, created_at DESC, id DESC)`。
- 活跃账户索引覆盖 billing held/capture_pending，以及 submitting、submission_unknown、queued、in_progress；新建但尚未进入 submitting 的 held 任务也必须占用长期并发。
- worker 索引覆盖 `next_action_at` 和过期 lease。

`input_manifest` 只保存 role、文件名、经 sniff 确认的 MIME、大小、SHA-256，以及图片输入由加密 reader 解码得到的宽高；文件名和派生宽高不参与 request hash。它不保存 spool 路径、媒体字节或客户端本地路径。`response_metadata` 必须过滤长期凭证和不受控 Provider 响应体。

### 7.2 video_task_events

事件表为只追加日志，记录：

- 本地状态转换和 version。
- Provider webhook event ID、provider/account/provider task ID。
- 原始状态、规范化状态及去敏 payload。
- 预占、结算、释放和人工处理。
- Provider 信息或凭证暴露审计。

允许 webhook 事件暂时没有 `task_id`，以处理创建响应尚未落库但 webhook 已到达的竞争。后续只能通过精确的 Provider task ID、client token 或 Provider 官方搜索能力关联，禁止相似度猜测。

### 7.3 video_callback_deliveries

保存用户 callback 的规范化 payload、事件指纹、加密目标 URL、状态、attempt、next attempt、lease 和 quarantine 信息。它不保存媒体字节，也不转发 Provider 原始 webhook body。

## 8. 状态机与不变量

### 8.1 正交状态

```text
generation:
preparing -> held -> submitting -> queued -> in_progress -> completed
                         |              |           |
                         +-> submission_unknown     +-> failed
                                        +----------> cancelled / expired

billing:
none -> held -> capture_pending -> captured
           +-> release_pending -> released
           +-> manual_review

delete:
none -> requested -> deleting -> deleted
                         +-----> delete_failed
```

### 8.2 强制不变量

1. 没有已提交的余额预占，不得发出 Provider 创建请求。
2. Provider、channel 和 account 自 `held` 起不可变。
3. 同一任务最终只能完成一次 capture 或 release。
4. 生成完成后，无论用户是否下载、下载是否失败，都按 Provider usage 结算。
5. 下载不得改变任务生成状态或资金状态。
6. polling 和 webhook 必须进入同一个单调状态转换函数。
7. 已完成状态不能被迟到的 queued/in_progress webhook 回退。
8. Redis 队列不是事实来源，删除 Redis 数据不能造成任务永久丢失。
9. `submission_unknown` 不自动换账号、不盲目重试、不自动退款。
10. 跨用户 GET、DELETE、content 均返回与不存在相同的 404。
11. 版本化执行规格、hash、原报价和成本快照不得被恢复流程重写；已确认的规格冲突不能通过清除响应字段或回退 billing state 消失。
12. 未最终结算的人工扣费/释放必须具备可归属个人身份、原因、脱敏证据引用、期望任务版本和操作幂等键；高风险动作经独立第二人审批。unknown 的确认未创建/认领无论金额均需独立第二人批准；提出申请不等于绑定或退款。已结算错误使用独立更正账本，不能修改原金融意图。

上述第 11-12 项的增量代码与本地证据见修复实施记录第 10-12 节。unknown 人工认领及未创建复核已经接入，但外部归属/证据真伪、可信上传计量、全部旧 writer 合同以及历史更正账本尚未全部完成。

## 9. 创建 Saga

1. 验证用户、API key、分组和功能开关。
2. 流式接收 multipart，写入加密 spool，构建稳定 request hash。
3. 规范化请求并通过模型目录验证输入 role、MIME、大小、时长和尺寸。
4. 对 prompt、远程参考图和上传参考图执行既有内容审核；拒绝或审核不可用时停止，且不创建任务或 hold。
5. 解析 public/channel/upstream model，选择 Provider、channel 和 account。
6. 在账户级 PostgreSQL advisory transaction lock 内检查长期任务并发。
7. 解析唯一售价规则和最大预占金额。
8. 单事务插入 `video_tasks`、claim hold idempotency、冻结余额、写 held 事件。
9. 单调转换为 `submitting`，持久化 stable client token 和 submit attempt。
10. 使用脱离客户端取消但有硬超时的 context 调用 `Provider.Create`。
11. 成功时原子保存 Provider task ID和 queued/in_progress 状态。
12. 明确拒绝时写 `failed + release_pending`，由 durable worker 释放预占。
13. 不明确时写 `submission_unknown`，保留冻结余额并进入隔离/对账流程。
14. 关闭所有输入 reader 并安全删除 spool。
15. 返回本地任务对象；若响应本身丢失，客户端通过相同 Idempotency-Key 获取原任务。

Provider 调用已经开始后，即使客户端断开，也应在独立的短时 submit context 中继续读取上游结果。只有客户端尚未完整上传请求体时，才跟随客户端取消并不创建任务。

## 10. Worker、轮询与 webhook

### 10.1 调度

- PostgreSQL 是权威任务源。
- Redis 只保存 poll、settlement、delete、callback 等 ready/delayed 工作。
- worker 使用数据库 lease、heartbeat、`next_action_at`、指数退避和 jitter。
- 周期 DB sweep 找回漏投递任务、过期 lease 和待结算任务。
- 创建提交由 HTTP 链路同步完成，不能把依赖临时 spool 的 Create 工作投递给其他实例。

### 10.2 账户亲和与并发

- 创建前在账户级事务锁中按数据库非终态记录计数。
- `submitting`、`submission_unknown`、`queued`、`in_progress` 和结算中的成功任务持续占用长期视频并发。
- 派生操作默认继承 parent 的 Provider 和 account。
- 请求级 Redis concurrency slot 只能限制短 HTTP 请求，不能代表持续数分钟或数小时的视频任务。
- RPM 可使用分布式滑动窗口；长期任务并发必须以数据库状态为准。

### 10.3 Provider webhook

1. 使用原始字节和 Provider 官方算法验签。
2. 解析 account/project 范围和 Provider event ID。
3. 先持久化并去重，再返回 2xx。
4. 精确关联任务并投递本地状态处理工作。
5. 无法关联的合法事件进入 unmatched 队列，等待精确关联或人工处理。
6. 轮询始终作为 webhook 丢失的补偿机制。

OpenAI project webhook 不能仅按 Provider task ID跨账户查询；关联键必须包含 Provider 和 account/project 上下文。

## 11. 下载代理

### 11.1 请求流程

```text
client GET/HEAD + Range
    -> local task ownership check
    -> generation completed + billing captured check
    -> load immutable provider/account affinity
    -> Provider.OpenContent
    -> filtered headers + streamed body
    -> client
```

### 11.2 行为要求

- 支持 video 默认内容以及 Provider capability 声明的 thumbnail、spritesheet 等 variant。
- 支持 `GET`、`HEAD`、单区间 Range、`If-Range`，并正确返回 200、206、416。
- 不在内存中读取完整内容，不写临时文件，不进入任何缓存。
- 客户端断开时立即关闭 Provider body 并取消上游 context。
- 采用固定大小复制 buffer，buffer 只存在于单次请求内。
- 设置独立的连接、首字节、空闲读取和总时长限制；总时长需允许大视频慢速下载。
- 下载并发按用户和 account 分别限制，但不占用视频生成并发。
- 只透传 `Content-Type`、`Content-Length`、`Content-Range`、`Accept-Ranges`、`ETag`、`Last-Modified` 等 allowlist header。
- 丢弃 Provider 的 `Set-Cookie`、认证头、内部 request ID和非公开存储 header。
- `Content-Disposition` 文件名由平台根据本地任务 ID生成，不信任上游文件名。
- 所有内容响应设置 `Cache-Control: private, no-store`。
- 已知任务但 Provider 内容已过期时返回 410 `video_content_expired`；非本人任务仍返回 404。

下载不参与生成费用计算。Provider 内容读取本身收费时，必须作为独立 billing unit 设计，不能隐式计入视频生成结算。

## 12. Provider 信息与凭证暴露

### 12.1 暴露策略

账户和分组分别配置 `provider_disclosure_policy`，取值：

| 策略 | 可返回内容 |
|---|---|
| `none` | 只返回本地任务字段 |
| `identity` | 增加 Provider 名称和上游任务 ID |
| `task_access` | 增加 Provider 签发的任务级临时 URL/token |
| `dedicated_credentials` | 对用户独享/BYOK 账户允许返回账户访问凭证 |

生效策略取系统、分组和账户三者中最严格的结果。默认值为 `identity`。

### 12.2 允许返回

- Provider 名称和区域。
- 上游任务 ID。
- Provider 官方签发且作用域仅限该任务或内容的短期 signed URL/token。
- 网关签发的单任务、短期下载 capability token。
- 用户独享或用户自己提供的 BYOK 凭证，且必须启用 `dedicated_credentials`。

### 12.3 禁止返回

- 共享账号池的 API key。
- 共享账号池的 OAuth access token 或 refresh token。
- session cookie、service-account JSON、私钥和可刷新长期会话材料。
- 能够访问同账户其他用户任务的 Provider 凭证。
- 任何通过 callback、日志、异常、指标或前端埋点间接泄露的凭证。

如果业务要求返回共享池长期凭证，则该账户不得继续参与共享调度，必须先转换为用户独享账户。这是账户所有权模型变化，不能通过一个响应字段开关规避。

### 12.4 存储与审计

- Provider 任务级访问材料如必须跨请求保存，使用现有密钥体系加密，并记录 scope 和 expires_at。
- 过期材料由清理 worker 擦除密文；任务 ID和披露审计继续保留。
- 每次披露记录 user、API key、task、credential kind、scope 和时间，不记录 credential value。
- 带凭证的字段不得进入用户 callback；callback 只包含 Provider identity、task ID和状态。

## 13. 预占、定价与结算

### 13.1 定价

视频价格规则使用结构化条件，不把多维条件编码进 `tier_label`。匹配维度至少支持：

- provider 和 model
- operation
- size、resolution、quality
- duration
- input type 和 input video duration
- audio enabled
- service tier

定价配置中的 `resolution` 是可自定义的规则维度键，不等同于 `usage_logs.video_resolution`。结算日志只能写入不超过 10 字节的规范 `WIDTHxHEIGHT` 或 `NNNp`；价格快照应另存 `usage_resolution`。历史任务无法从 Provider size 或模型名确定规范值时允许留空，不能截断内部键，更不能让这一可选描述字段阻断 capture/release。
- 生效时间区间

规则选择先过滤全部条件匹配项，再按显式 priority 和 specificity 选取；同优先级、同 specificity 出现多个候选时拒绝创建，不能随机选价。

任务保存不可变价格快照：billing unit、unit price、estimated/actual units、规则 ID和版本、group/account multiplier、客户币种，以及单独的 Provider 成本币种和成本规则。

### 13.2 预占

- Provider 提交前必须完成余额冻结。
- hold 使用请求允许的最大计费量，而不是平均值。
- 无法计算有限最大成本的能力不能开放创建。
- hold request ID使用 `video_task_hold:<local_task_id>`。
- 预占与任务 held 状态必须在同一个数据库事务中完成。

### 13.3 结算

终态转换和 settlement intent 在同一事务中写入。扩展既有 `usage_billing_outbox`，由 Complete 事务原子完成：

1. claim `video_task_capture:<local_task_id>` 或 release request ID。
2. 减少 frozen balance。
3. 退回预占差额或补扣超额。
4. 更新 API key、account 和平台额度。
5. 写入 `usage_logs`。
6. 更新 `video_tasks.billing_state`。
7. 完成 outbox event。

实际费用超过预占时允许视频 scope 原子补扣至负余额，并耐久化禁止继续创建付费任务的后效；Batch Image 仍保持现有超额拒绝语义。

计费结果不能只由 generation status 决定：

- 提交前失败：release。
- Provider 明确拒绝且未创建任务：release。
- Provider 接收后的 failed/cancelled：按 Provider usage 和价格规则决定 capture 或 release。
- completed：capture，和用户是否下载无关。
- submission_unknown：保持 held，进入 manual review。
- delete：不会自动退款，必须先根据 Provider 实际结果完成结算。

## 14. 删除语义

| 状态 | 行为 |
|---|---|
| `held` 且尚未调用 Provider | 阻止提交，释放预占，写 tombstone |
| `submitting` / `submission_unknown` | 返回 409，等待精确收敛或管理员处理 |
| `queued` | 优先调用 Cancel/Delete；按 Provider usage 结算后 tombstone |
| `in_progress` | 遵循 Provider cancel/delete capability；不伪造成功 |
| `completed` | 先完成 capture，再删上游内容，最后 tombstone |
| `failed` / `cancelled` / `expired` | 完成 capture/release 后删除上游并 tombstone |

本地任务行、事件和 usage log 不物理删除。删除后的内容接口返回 404；管理员仍能查询审计记录。

## 15. 用户 callback

- `callback_url` 通过 HTTPS、域名、端口、DNS 和解析后 IP 双重校验。
- 禁止 loopback、链路本地、内网、metadata endpoint 和重定向逃逸。
- callback 使用专用 HTTP transport，禁用系统代理和自动重定向。
- payload 为平台规范化事件，如 `video.completed`、`video.failed`、`video.cancelled`。
- 每个 payload 包含 local task ID；Provider identity 和 upstream ID根据 disclosure policy 返回。
- callback 不包含账户级凭证或媒体字节。
- 使用平台独立 HMAC 密钥签名，包含 timestamp、event ID和 body hash。
- 通过 outbox lease、指数退避和最大重试窗口保证投递；耗尽后 quarantine 并告警。
- completed callback 只有在 capture 成功后可见，failed/cancelled callback 只有在 capture/release 收敛后可见。

## 16. 安全与隐私

1. 下游 Authorization 永不转发；上游认证只来自绑定 account。
2. prompt 和标量请求只在提交期间存在于内存；数据库保存 request hash 和计费派生字段，除非未来明确启用加密审计策略。
3. 媒体输入只存在于加密 spool，媒体输出只存在于代理网络流。
4. spool 文件、Provider URL和 credential value 不进入日志、trace、metrics、panic dump 或审计 body。
5. API body 审计遇到视频路由必须记录摘要而非原始 multipart。
6. 返回 Provider 凭证前同时验证任务 owner、account owner 和 disclosure policy。
7. 跨用户任务访问始终使用相同 404，不能通过 content、delete 或 provider ID探测。
8. Provider 响应 JSON必须经过字段级过滤后才能保存快照或返回。
9. 下载代理必须限制响应 header、重定向、最大并发和空闲连接，防止成为开放代理。
10. 所有加密使用认证加密并支持密钥轮换；数据库和 spool 使用不同用途密钥。

```yaml
      total_timeout_seconds: 3600
    callback:
      enabled: true
      retry_hours: 24
      request_timeout_seconds: 15
      signing_secret: ${VIDEO_CALLBACK_SIGNING_SECRET:-}
```

Provider 的真实输入上限由模型目录决定，网关全局上限只是系统保护上限，最终取二者较小值。

## 18. 可观测性与管理能力

核心指标：

- 各 Provider/status 的任务数和状态停留时间。
- submit latency、poll latency、webhook delay。
- submission_unknown 数量和冻结金额。
- 全部未结算 hold 金额、最老 settlement pending 和最老 manual review 时长。
- hold、capture、release、over-capture 次数和金额。
- Redis ready/delayed/active 队列深度，以及 DB sweep/lease 恢复次数和条目数。
- spool 当前/最大字节数、利用率、活跃 session、孤儿候选和清理失败数。
- content proxy 并发、首字节、传输字节、客户端中断和上游错误。
- webhook 去重、未关联和验签失败。
- callback duration、重试、quarantine 和投递延迟。
- Provider credential disclosure 次数，按 kind 和 policy 聚合，不带 value。
- 账户 capability probe 的 `supported`、`unsupported` 和 `unknown` 次数。

管理端至少提供：

- 按用户、Provider、account、状态和时间筛选任务。
- 查看状态事件、计费快照、hold 和 settlement 状态。
- 查看并处理 submission_unknown/manual_review。
- 重放 polling、settlement、delete 和 callback；不得提供无保护的 Create 重放。
- 查看能力目录，并查询或手工触发单账户 capability probe。
- 查看安全的 spool 健康信息：enabled、active sessions、current/max bytes、utilization、orphan candidates、last sweep/result、cleanup failure count，以及 Redis queue 状态和深度；不得返回目录、文件名、媒体、hash 或加密材料。
- 查看凭证披露审计，但不能查看已披露值。

## 19. 失败点处理矩阵

| 失败点 | 持久状态 | 资金 | 自动动作 |
|---|---|---|---|
| multipart 校验失败 | 无任务 | 无 hold | 删除 spool，返回 400 |
| hold 失败 | 无可提交任务 | 不冻结或事务回滚 | 删除 spool，返回余额错误 |
| 提交前内部失败 | `failed` | `release_pending` | durable release |
| 上游明确拒绝 | `failed` | `release_pending` | durable release |
| 上游响应超时/断开 | `submission_unknown` | 保持 held | webhook/search/人工收敛 |
| 上游成功但 DB 保存失败 | `submission_unknown` 或 stale submitting | 保持 held | client token/webhook 精确关联 |
| Redis 入队失败 | DB 状态不变 | 不变 | DB sweep 重建 |
| webhook 重复或乱序 | 单调状态不回退 | 幂等 | 去重后忽略或推进 |
| settlement 暂时失败 | `capture_pending/release_pending` | 保持可恢复 | outbox 重试 |
| 下载中断 | generation 不变 | 已结算不变 | 关闭上游流，不自动重试 |
| Provider 内容过期 | task 仍 completed | 已结算不变 | content 返回 410 |
| callback 失败 | delivery pending/failed | 不变 | 重试后 quarantine |

## 21. 验收门禁

### 21.1 API 与 Provider

- OpenAI 官方 multipart 示例可以创建纯文本、参考图和参考视频任务。
- input part 顺序变化不影响解析、定价或 Provider 请求。
- create/get/list/delete/content 的公开响应通过 golden test。
- Provider 不支持的 input role、variant 或操作稳定返回 capability 错误。
- 公开 ID与上游 ID不会混淆，跨用户访问全部为相同 404。

### 21.2 媒体零持久化

- 测试期间监控系统临时目录和应用目录，确认默认 multipart 不会产生明文文件。
- spool 文件始终为密文，正常、失败、取消和 panic 恢复后均能清理。
- video、thumbnail、spritesheet 下载过程中没有完整响应体内存缓冲或文件写入。
- 数据库、Redis、日志和 callback 均不包含媒体字节。

### 21.3 一致性与计费

- 在 hold、状态转换、Provider 请求、响应落库和结算每个边界注入故障。
- 重复创建、重复 webhook、重复 outbox 和 worker 并发不会双扣或重复释放。
- Redis 全量删除后，PostgreSQL sweep 能恢复全部应执行工作。
- submission_unknown 不重试、不换账号、不释放冻结款。
- 余额守恒满足 `balance + frozen_balance + captured/refunded delta` 的事务不变量。
- Batch Image 既有 request ID、超额拒绝和在途任务行为完全不变。

### 21.4 下载与安全

- HEAD、正常下载、合法 Range、非法 Range、慢客户端和中途断开均正确处理。
- Provider credential/header/cookie 不会通过代理响应意外透传。
- shared account 的长期凭证在所有 API、callback、日志和错误中均不可见。
- dedicated/BYOK 凭证只有 owner 在策略允许时可见，并产生不含 value 的审计事件。
- callback 通过 SSRF、DNS rebinding、redirect、HMAC、重放和超时测试。

## 27. Provider principal/alias 核验需求落地补充（2026-09-05）

1. dedicated root account 的 `verified` 状态必须绑定当前 `provider_identity_version` 的唯一 active binding；旧 verified 数据不满足该条件时必须降级，不得兼容放行长期凭据。
2. 提案人和批准人必须是两名不同的当前 active admin，申请事实、identity version、principal/origin hash、理由、证据和操作幂等键不可原地改写。拒绝不改变账户，批准与 binding/account/outbox 同事务提交。
3. principal 原值、base URL 原文、凭据、完整 hash 和 Provider 响应不得出现在数据库 review facts、Admin DTO、浏览器历史或日志；只允许展示短指纹用于人工交叉核对。
4. 相同已登记 principal 不得跨 owner；可识别到的相同 API key/token/project/account alias 若存在 shared、其他 owner 或 revoked 记录，批准与调度都必须 fail-closed。相同 owner 的 dedicated alias 可分别审批并共享撤销域。
5. 紧急撤销无需第二人，但要求 active admin、reason、evidence 和稳定操作 key；同一 principal 的全部当前 binding 与账号必须原子 revoked/不可调度，且不可原地恢复。
6. migration 264、Repository、Service、Admin API/UI 和单元/集成/前端测试实现上述本地合同。Provider API 自动验真、证据真实性、系统外 alias 完整性、legacy 候选提升及生产混跑仍是后续强制需求。

## 28. multipart 共享创建意图需求落地补充（2026-09-05）

1. 原生 OpenAI 与 Composite managed multipart 的文件部分必须直接流入加密 spool；不得为了幂等 hash、模型路由或安全审核把完整上传文件读入普通内存或新增明文临时文件。
2. multipart 请求身份使用 `canonical_multipart_v1`：每个 part 至少绑定字段名、是否文件、文件名、规范化 MIME、字节长度和内容 SHA-256。boundary 和不同字段排列不改变同一语义；重复文件字段的顺序属于语义，内容、文件名、MIME、scalar 或 JSON/multipart 合同变化必须返回幂等冲突。
3. 解析必须拒绝未知/重复 part header、`Content-Transfer-Encoding`、重复 scalar、scalar/file 同名、未知 scalar/文件角色、空文件名、控制字符、超大 scalar、过多 part 和截断输入；重复的受支持二进制角色可以保留并按顺序参与 hash。
4. 加密 spool 完成并得到规范 hash 后，必须在 Composite 路由、生成预算/RPM、hold 和 Provider Submit 前领取共享意图。原生 task/hold 与 intent 的绑定仍由数据库原子完成；失败 hold 不得留下 native binding。
5. 已绑定 native task 的重放必须固定回原生任务读取路径，不重新解析当前 Composite 映射、不重新预算、不重新 hold，也不得因当前路由改为 Grok 而再次提交。相同 key 的在途请求继续返回可重试的进行中结果。
6. Composite managed multipart 解析完成后才按可信 scalar/source 解析路由：命中 OpenAI 继续原生路径；命中 Grok 时通过 `io.Pipe` 从加密 spool 重建 multipart，并以请求大小上限包裹下游 body，不产生第二份明文磁盘副本。
7. 该补充不新增 migration，复用 migration 254 的 `request_contract/request_hash` 和现有 native binding。旧 video writer 不理解流式 multipart 仲裁，会绕过这一合同；发布前必须停止全部旧 video writer，再部署完整新路由/handler/service，不能滚动混跑后直接放流。

## 29. legacy Grok 候选可信提升需求补充（2026-09-05）

1. 只有 `manual_review`、尚未绑定 durable intent、快照 hash 已验证、当前 Group/account/identity 仍可验证且拥有完整冻结计费快照的归档候选，才允许提出 `promote`。缺少创建期可信 principal 的事实不得由当前默认值、当前价格或另一账户补造。
2. 提案必须绑定 import version、冻结事实、reason、稳定 operation key、证据引用和完整 64 位十六进制 SHA-256；Admin API/UI 只展示证据 hash 的短指纹，不回显 Redis key、session hash、原 payload、凭据或 Provider 原始响应。
3. 批准人必须是不同的当前 active admin，且提出人在批准时仍为 active admin。批准采用“短事务锁定和预检 → 释放全部数据库锁 → 冻结账号精确 Provider GET → 最终事务重新校验并原子提交”，不得在网络调用期间持有 import/account/user 行锁。
4. Provider 观察只接受唯一安全字符串任务 ID 且与归档 ID 完全一致；只允许 `done + billable=true`，或 `failed/expired + billable=false`。其他状态、重复 JSON 键、URL/路径 ID、疑似凭据、身份版本变化或账号拓扑变化一律 fail-closed。

## 30. legacy Grok 双人账务结论需求补充（2026-09-05）

1. legacy 提升与账务处置是两个独立审批域。promotion review 的批准不能直接触发计费；后续 `retry_billing`、`confirm_existing_usage` 或 `waive` 必须分别创建新的 Grok job review，并由不同 active admin 批准。
2. `retry_billing` 仅允许 Provider 已完成且当前 request ID/API Key 下不存在 usage、active dedup 和 archive dedup。只要任何一种账务痕迹存在，就不得通过重试制造第二条 usage 或重复扣款。
3. `confirm_existing_usage` 仅允许存在 usage 且 active/archive dedup 至少一个存在，并且 usage 与冻结 job 事实逐项一致：user、API Key、Group、account、model、billing mode/type、subscription、total/actual cost、customer/account multiplier、video count、resolution 和 duration 均不得依赖模糊匹配或当前配置。
4. 确认既有 usage 只把 job 标记为 `billed` 并记录 `legacy_existing_usage_confirmed` 与审批引用；不得调用 RecordUsage、重复扣余额、追加 usage/outbox 或重复消费任一 quota。
5. 任何 usage/dedup 存在但不匹配时，`retry_billing` 和 `confirm_existing_usage` 都必须阻断。管理员只能在有充分证据时选择独立双人 `waive`，或保持 `manual_review` 等待历史已结算更正账本；不得原地修改旧 usage、金额或 dedup 来使检查通过。
6. review facts 必须冻结具体 usage 行、dedup 来源与指纹以及 `exists/matches` 派生结果；批准时重新计算并复核。UI 只能在后端派生证据允许时展示重试或确认入口，前端隐藏按钮不能替代数据库约束。

## 31. durable 账务副作用证据保留需求补充（2026-09-05）

1. `usage_billing_outbox` 不能在成功后成为一次性证据。任何 `result.applied=true` 或 `projection_repair_required=true` 的 stage-1 行，必须在同一数据库事务生成不可变 `usage_billing_effect_archive` 后才允许删除。
2. archive 必须保留 request/API Key/fingerprint、payload version、精确 command payload、result payload、首次 source outbox ID/时间，以及白名单 usage facts。不得复制 prompt、媒体字节、credential、cookie、Authorization、user-agent、IP 或 session ID。
3. 正常幂等重放若没有产生新账务副作用，不得新建或覆盖 archive。相同 request/API Key 再次出现实际副作用时，只有精确相同的 command/result/usage facts 才可视为一致；冲突必须回滚账务事务。
4. archive 只能由 outbox stage 转换触发器创建，业务 API、管理员或普通 SQL 不得直接插入；UPDATE/DELETE 永久拒绝。应用过副作用的 outbox 若找不到匹配 archive，也不得被确认删除。
5. migration 267 应回填迁移时仍存活的 applied/projection-repair stage-1 outbox。已经被旧版本 acknowledge 并物理删除的历史 outbox 无法安全重建，不得从 dedup fingerprint 或 usage row 猜测原 balance/subscription/Key/平台/账户 quota 分配。
6. effect archive 是更正账本计算“原始实际副作用”的证据源，不是更正动作本身。后续 correction preview/review/apply 必须继续双人审批、冻结当前计数器、产生独立 adjustment entry，并且不得修改 archive、原 usage 或原 dedup。

## 32. legacy 历史账务更正只读预览需求补充（2026-09-05）

1. 预览只适用于已提升 legacy job 的 `manual_review + provider done + legacy_billing_reconciliation_required + usage exists + usage mismatch`。普通 keyed job、无 usage、完全匹配 usage、failed/expired 或 waived/billed job 不应生成 correction preview。
2. 后端必须从 `usage_billing_effect_archive` 解码实际 command，并与 archive 中不可变 usage facts 交叉校验 request、user、API Key、Group、account、subscription、model、billing type、total/actual cost。不能改用当前 usage 行或当前配置替代 archive。
3. “应有 effect”来自 job 冻结 `GrokVideoPricingSnapshot` 与创建身份；实际启用过的 API Key quota/rate-limit、account quota 和平台 quota policy 只可沿用 archive command 的已证明开关，不能凭当前配置开启新的更正维度。
4. 若实际 account 与冻结 account 不同，冻结快照不包含目标账户当时的 quota-limit 开关，必须产生 `account_quota_policy_unknown`。若历史为 subscription、应有为 balance 且实际 command 没有平台 quota effect，必须产生 `platform_quota_policy_unknown`。
5. preview 必须包含实际/应有 effect、实际/应有 usage 和 `desired - actual` 金额差额；usage 侧至少比较客户倍率、账户倍率、模型、billing mode/type、subscription、数量、分辨率和时长。完整 fingerprint 不得返回，最多展示 16 位短指纹。
6. `safe=true` 只表示“当前 archive 足以形成后续受审 adjustment 计划”，不表示允许立即执行。管理端必须只读展示，没有 proposal/approve/apply 按钮、没有余额或 quota mutation，也不能把 safe preview 当作已完成更正。
7. archive 缺失、未来 payload version 未支持、非法 effect origin、非 Grok/video command、金额/分配非法、usage facts 缺失或冲突时，详情仍可返回但 `safe=false` 并列出稳定 blocker code，不因预览失败使整个管理列表不可用。

## 33. legacy 历史账务更正授权计划需求补充（2026-09-06）

1. correction proposal 只能从当前完整、安全且需要调整的 preview 创建，不接受客户端上传 arbitrary actual/desired/delta、金额或财务维度。服务器必须在事务内重新构建 preview。
2. proposal 必须冻结 job review version、archive request/API Key/full fingerprint/payload version/effect origin、完整 preview、数据库计算 preview hash 和包含 job/archive/usage 的 source facts。
3. review 与 action 永久不可变；直接 approved INSERT、自审批准、非 active admin、提出人已失效、陈旧版本/事实、伪造 hash/source facts 和重复 approved plan 必须由数据库拒绝。
4. proposal/approve/reject 都必须要求个人管理员身份、`If-Match`、稳定 `Idempotency-Key`、4-1024 字符 reason 和脱敏 evidence reference；API 不返回 credential、raw command/result 或完整 archive fingerprint。
5. 同一 intent 最多一个 pending correction review，且普通 Grok billing review pending 与 correction pending 双向互斥。同一 job version/preview 最多一个 approved plan。
6. 批准时必须重新读取 archive 并重建 preview，验证 review.preview/hash/source facts 仍一致；任何 job、archive、usage 或 eligibility 变化使批准失败。拒绝只关闭计划，不修改业务 job。
7. approve 不表示 correction completed，不得更新 job billing/resolution/version，不得写余额、subscription、API Key/平台/账户 quota、usage、dedup 或 billing outbox。UI 必须持续显示“授权计划，未执行”。
8. 后续 apply 需求必须单独设计 adjustment ledger、当前财务事实 CAS、每维分录、原子资金/usage/quota 应用、post-effects outbox、幂等恢复、人工对账与撤销策略；不得复用 review status 作为执行结果。

## 34. legacy 历史账务更正执行需求补充（2026-09-06）

1. apply 只能引用 `status=approved` 且尚无 execution 的 correction review，不接受客户端传入金额、actual/desired、delta、target、window 或 usage 内容。
2. command 必须绑定 intent、review、个人执行管理员、当前 job version、稳定 operation key、request hash 和 reason。执行管理员必须为当前 active admin 且不能是提出人；相同 operation key/相同请求可重放，不同请求必须冲突。
3. 数据库必须在一个事务内重新验证 review.preview hash、source facts、archive identity、legacy mismatch eligibility、job/review version 和无 pending review，并锁定所有受影响财务行与原 usage。
4. 每个资金/额度维度必须生成独立不可变 entry，至少包含 execution、dimension、target kind/id、source cost delta、实际 counter delta、before、after、window start 和 created time；`after=before+applied delta` 由数据库约束。
5. user balance、subscription daily/weekly/monthly、API Key total/5h/1d/7d、account total/daily/weekly 和 platform daily/weekly/monthly 必须使用完整旧值 CAS。任一目标缺失、窗口证据不足、结果为负或当前事实变化，整个 command/execution/资金/job 事务必须回滚。
6. rate window 已过期时不得污染当前窗口；仍可保存 source delta，但 applied delta 必须为 0。是否调整 account daily/weekly 只能沿用 archive result 证明的历史 policy。
7. 原 usage、dedup、dedup archive 和 effect archive 永久不变。另建 correction usage audit 保存原 usage ID 与 actual/desired usage；job 成功后绑定唯一 execution、增加 review version 并进入 `billed`。
8. 同一事务必须创建不可变缓存投影 outbox。多实例 Worker 使用 PostgreSQL 租约处理重放安全的 cache invalidation/refresh；临时失败重试、无效 payload 隔离、进程重启可接管。apply API 成功不等于缓存已经 terminal。
9. Admin API/UI 必须把 apply 作为与 approve 分离的高风险动作，要求 `If-Match`、`Idempotency-Key`、reason 和二次确认；只在 approved/unexecuted 时显示，执行后展示 ledger，不提供删除或页面撤销。
10. 上线验收必须包含并发双 apply、同 key 重放/冲突、提出人执行、陈旧 source facts、负 counter 回滚、subscription 计费目标迁移、过期 window、outbox ack 前崩溃/重启、Redis 故障和多实例租约接管。
