## 0. 方案结论

本方案在当前 `main` 分支上新增通用视频任务底座，并将 OpenAI Videos 接入该底座。核心事实源是 PostgreSQL 的 `video_tasks`，而不是 Redis、上游任务列表或客户端持有的 Provider ID。

首版实现的能力范围：

- `POST /v1/videos`：纯文本和 `input_reference` 图片创建。
- `POST /v1/videos/characters`：上传 MP4 创建可复用 character 元数据映射。
- `POST /v1/videos/edits`：上传视频编辑。
- `POST /v1/videos/extensions`：引用已有视频任务进行延展。
- `GET /v1/videos/{id}`、`GET /v1/videos`、`DELETE /v1/videos/{id}`。
- `GET/HEAD /v1/videos/{id}/content`，支持 `video`、`thumbnail`、`spritesheet` 和 Range 流式代理。
- OpenAI webhook、平台轮询、用户 callback、余额预占/结算和异常人工收敛。

媒体边界：

- 不建设 `AssetStore`，不建设 `video_assets`。
- 输出视频、缩略图和 spritesheet 不落盘、不缓存、不进入数据库。
- 输入媒体使用加密短期 `SubmissionSpool`，只服务当前 HTTP 请求中的 Provider 提交；Provider Create/Edit/Character 返回后立即删除。
- character 是上游可复用资源，因此只增加 `video_resources` 元数据表，保存 owner、Provider、account、上游 resource ID 和过期/删除状态，不保存 MP4。

安全边界：

- 可返回 Provider 名称、上游任务 ID和任务级短期访问 token/URL。
- 共享账号池 API key、OAuth token、refresh token、cookie、service account 私钥永不返回。
- OpenAI 首轮只调度 API Key 账户；自定义 Base URL 必须显式声明 videos capability；OAuth、SetupToken、Azure 不参与首发调度。

## 1. 当前主分支落点与前置门禁

## 2. 分层架构与依赖方向

```text
OpenAI /v1/videos          Grok compatibility          Native provider routes
         |                         |                           |
         +---------------- Protocol Adapters -----------------+
                                   |
                            VideoTaskService
              create/get/list/delete/content/resource
                                   |
       +---------------------------+--------------------------+
       |                           |                          |
 VideoProviderRegistry    Reservation/Settlement       SubmissionSpool
       |                           |                  (request-scoped only)
 OpenAI / future adapters  hold + outbox + usage               |
       |                           |                          |
       +----------------------- PostgreSQL -------------------+
                                   |
                    Redis queues + workers + sweepers
```

必须保持以下依赖关系：

- `handler` 只负责协议解析、鉴权、响应投影和流式 HTTP 输出。
- `VideoTaskService` 负责领域校验、账户绑定、状态机、幂等和资金事务编排。
- `VideoProvider` 负责上游 HTTP 协议、Provider 错误和响应 DTO；不得依赖 Gin、余额或 SQL 表。
- `Repository` 负责 SQL、乐观锁、lease 和事件持久化；不得解析 OpenAI 字段。
- `Billing` 负责 hold/settlement，不依赖具体 Provider。
- `SubmissionSpool` 只提供受控输入 reader，不提供资产查询或下载接口。

## 4. 公共 API 实现

### 4.1 路由表

| 方法 | 路径 | Handler 行为 |
|---|---|---|
| POST | `/v1/videos` | create；JSON 或 multipart，支持文本和图片 input_reference |
| GET | `/v1/videos` | 本地 owner list，稳定 cursor 分页 |
| GET | `/v1/videos/:video_id` | 本地任务 + 必要时刷新状态 |
| DELETE | `/v1/videos/:video_id` | 上游删除/取消 + 本地 tombstone |
| GET/HEAD | `/v1/videos/:video_id/content` | Provider 流式代理，`variant` 默认 video |
| POST | `/v1/videos/characters` | multipart MP4 上传并创建 character resource |
| GET | `/v1/videos/characters/:character_id` | 查询 resource 元数据和状态 |
| DELETE | `/v1/videos/characters/:character_id` | 删除上游 resource 并 tombstone |
| POST | `/v1/videos/edits` | JSON 引用已有 video 或 multipart 上传视频 |
| POST | `/v1/videos/extensions` | 引用已有 video 任务，创建派生任务 |

所有 `/v1` 和根路径兼容 aliases 共用同一 handler。旧 `/v1/videos/generations`、`/edits`、`/extensions` Grok 路径只对 Grok group 继续有效；OpenAI group 不能再落到 `GrokMedia`。

### 4.2 鉴权与归属

- `VideoHandler` 从现有 API key middleware 取得 `user_id`、`api_key_id`、`group_id`。
- task/resource 访问条件必须包含 `user_id`；命中他人或不存在统一返回 404。
- API key 只作为创建归因和计费对象，不作为任务访问主键；key 轮换后同一用户仍可访问任务。
- `provider_task_id`、`provider_resource_id` 只能作为响应字段，不能直接作为用户查询主键。

### 4.3 Idempotency-Key

- 唯一范围：`user_id + endpoint + idempotency_key`。
- request hash 包含规范化标量、operation、模型映射、每个 input role/MIME/size/SHA-256 和 Provider 扩展字段。
- 相同 key/hash 返回原任务或原 resource。
- 相同 key/不同 hash 返回 HTTP 409 `video_idempotency_conflict`。
- 为 characters、edits、extensions 分别使用独立 endpoint 命名空间，避免同一 key 跨操作碰撞。

## 5. 领域接口和 DTO

### 5.1 基础 Provider 接口

```go
type VideoProvider interface {
    Name() string
    Capabilities() VideoCapabilities
    SupportsAccount(account *Account) bool

    Create(ctx context.Context, account *Account,
        request VideoCreateRequest, inputs []VideoInput) (*ProviderVideoTask, error)
    Get(ctx context.Context, account *Account,
        ref ProviderTaskRef) (*ProviderVideoTask, error)
    OpenContent(ctx context.Context, account *Account,
        request ProviderContentRequest) (*ProviderContent, error)
    Delete(ctx context.Context, account *Account,
        ref ProviderTaskRef) error
}
```

基础接口不包含 `List`，因为用户列表必须来自本地 `video_tasks`。可选接口：

```go
type VideoCanceller interface { Cancel(context.Context, *Account, ProviderTaskRef) error }
type VideoEditor interface { Edit(context.Context, *Account, VideoEditRequest, []VideoInput) (*ProviderVideoTask, error) }
type VideoExtender interface { Extend(context.Context, *Account, VideoExtendRequest) (*ProviderVideoTask, error) }
type VideoCharacterProvider interface { CreateCharacter(...); GetCharacter(...); DeleteCharacter(...) }
type VideoTaskSearcher interface { SearchByClientToken(...) (*ProviderVideoTask, error) }
type VideoWebhookVerifier interface { VerifyWebhook(...) (ProviderWebhookEvent, error) }
```

缺少能力时在账户选择和 hold 前返回 `video_capability_unsupported`，不调用上游后再把 404 解释成能力不足。

### 5.2 规范化输入

```go
type VideoInput struct {
    Role     VideoInputRole // input_reference, source_video, character_clip, mask, ...
    FileName string
    MIMEType string
    Size     int64
    SHA256   string
    Open     func(context.Context) (io.ReadCloser, error)
}
```

`Open` 只能在当前提交请求内使用；禁止暴露本地 spool 路径。Provider 必须消费并关闭所有 reader 后才返回。

`VideoCapabilities` 同时声明 operation 到 input role 的允许关系、每个 role 的 MIME 集合和大小上限。multipart 层只校验 role 是长度受限的 ASCII 标识符并完成加密暂存，不把 Provider role 写死在 spool 中；账户和 Provider 确定后，再由 capability 在 hold 前决定该 operation 是否允许该 role。这样新增 `depth_map`、`mask`、`audio_reference` 等 Provider 二进制输入只需扩展 capability 和 adapter，OpenAI 内置目录仍严格限制为官方支持的图片 reference、上传 edit 视频和 character MP4。

`VideoCreateRequest` 包含 operation、local task ID、stable client token、requested/public/channel/upstream model、prompt、seconds、size、quality、audio、parent resource references 和 Provider 扩展字段。

`ProviderVideoTask` 至少返回 provider task ID、规范化 status、progress、usage、error、created/finished time、content variants、expires_at 和可选任务级 access token。

### 5.3 OpenAI 账户 capability

新增独立 `OpenAIEndpointCapabilityVideos`，不能复用现有 Grok media capability。账户选择规则：

- `AccountTypeAPIKey` 才进入首发候选。
- 标准官方 Base URL 可通过配置/健康探测获得 videos capability。
- 自定义 Base URL 必须在账户 capability 或模型目录中显式声明 videos，不能从 chat/responses capability 推导。
- OAuth、SetupToken、Azure 账户首发直接排除；后续适配必须单独验证认证和内容权限。
- 账户 capability 的未知状态不参与创建调度，管理端可显示为待探测。

OpenAI adapter 实现可选 `VideoCapabilityProber`，通过非计费 `GET /v1/videos?limit=1` 返回 `supported|unsupported|unknown`。结果只在 `accounts.extra.video_capability_probe` 保存 Provider、capability、状态、检查时间、HTTP 状态和脱敏错误码；API key、响应正文和 URL 不保存。账号创建/更新后异步探测，后台再以有界分页周期刷新；transient `unknown` 使用更短重试窗口。自定义 Base URL 即使探测可达，也必须保留显式 `openai_capabilities` override 才能参与调度。

## 6. OpenAI Provider 实现

### 6.1 请求映射

OpenAI adapter 只接受已经规范化的 DTO，不在 adapter 中做账户选择或计费：

- `Create` 映射到 OpenAI videos create。
- `input_reference` 只允许图片文件或 JSON 的 `file_id/image_url`，图片 MIME 为 `image/jpeg`、`image/png`、`image/webp`，并使用加密 spool reader 解码真实宽高后校验与目标 size 完全匹配；声明 MIME 与 sniff 结果不符时以 sniff 结果为准。`image_url` 和上传图片进入既有图片安全审核，上传图片以流式 Base64 构建有界审核体；当前全局审核上限为 8 MiB，超限在 task/hold 前拒绝。
- `file_id` 首版只允许当前用户独享/BYOK 的 OpenAI API Key 账户，并固定使用该账户；没有 `AssetStore`/文件归属表时，共享账户池不能安全接收任意上游文件 ID。
- 参考视频不映射到 `input_reference`。官方 OpenAI 视频仍通过 `Edit` 或 `CreateCharacter` 使用视频文件；显式声明 videos capability 的自定义 OpenAI-compatible Base URL 可在 `Create` 中接收并转发经过校验的 `reference_videos` 公网 URL，以及同一兼容协议的 `ratio` / `aspect_ratio`、图像、首尾帧和音频参考字段。官方 `api.openai.com` 不接收这些扩展字段。
- 当前发布的 `Edit` 允许本地 video task ID 或当前用户已有的 Provider video ID；multipart 上传视频仍由发布门禁关闭，待可信输出规格和硬上界验收完成后再开放。Provider capability 仍负责判断上游是否支持编辑。
- `Extend` 只引用已完成且仍可访问的 Provider video task；派生任务继承原 Provider/account。
- `CreateCharacter` 上传短 MP4，保存返回的 Provider character ID 到 `video_resources`。
- `OpenContent` 调用 task content endpoint，传递 variant 和 Range。
- `Delete` 根据资源类型调用视频或 character 删除；Provider 返回已不存在视为幂等成功。

### 6.2 HTTP 与认证

- 复用 `HTTPUpstream`、OpenAI profile、账户代理、TLS 指纹和认证头构建逻辑。
- 每次请求只使用 task 固定的 account；不使用现有普通文本的 credential failover。
- 上传请求使用 multipart writer，将 `VideoInput.Open()` 得到的 reader 分块复制到上游；禁止先读入 `[]byte`。
- 对 JSON 请求使用受控 encoder，过滤内部字段和用户 Authorization。
- 上游响应 JSON 设置最大读取上限；content body 走流式，不经过 JSON 读取器。
- 上游错误保留 provider code/status 和脱敏 message，禁止把 Authorization、签名 URL query 或 cookie 写入错误。

### 6.3 错误分类

| 情况 | Provider 错误 | 本地行为 |
|---|---|---|
| 参数/MIME/能力拒绝 | `rejected`, non-retryable | `failed + release_pending` |
| 认证/权限失败 | `rejected`, non-retryable | 标记账户能力/健康异常，release |
| 429/暂时过载 | `unknown` for create, retryable for Get | create 进入 unknown；Get 延迟重试 |
| HTTP timeout/连接断开 | `unknown` | `submission_unknown`，不换账号不退款 |
| 成功响应解析失败 | `unknown` | 保留 held，进入人工/搜索收敛 |
| Get 404 | 需结合任务状态 | 已确认不存在才终止，否则进入 review |

## 7. SubmissionSpool

### 7.1 设计目标

multipart 字段和文件 part 可以任意顺序出现。平台要先得到完整的模型、输入类型和媒体大小，才能选择 account、计算 hold 并调用 Provider，因此必须有请求级短期暂存。

SubmissionSpool 不是资产存储：

- 没有公共 API、业务 ID、下载能力或复用能力。
- 不进入 `video_tasks` 的长期媒体字段，也不进入 `video_resources`。
- 不保证进程崩溃后恢复读取；崩溃后的残留只能删除。
- 只在 Provider Create/Edit/Character 返回前有效。

### 7.2 解析流程

1. handler 读取 `Content-Type`，对 multipart 使用 `multipart.NewReader`。
2. 逐 part 校验 name、filename、role、MIME、重复字段和大小上限。
3. 标量字段进入受限内存结构；文件 part 流式写入 spool，同时计算 SHA-256、字节数和 MIME sniff；图片再通过加密 reader 解码真实宽高，媒体字节不回读到完整内存。
4. 完成所有 part 后执行 capability、模型、尺寸、时长、内容审核、价格和账户校验。
5. 创建 `video_tasks`/`video_resources` 和 hold 后，Provider 读取 spool reader。
6. Provider 返回后关闭 reader 并删除所有 spool 文件。

禁止使用 `Request.ParseMultipartForm` 或任何未指定目录的默认 multipart 解析，避免框架把明文文件写入系统临时目录。

### 7.3 加密与清理

- 每个 spool 使用随机文件名、随机数据密钥和随机 nonce。
- 文件采用固定大小 chunk 的 AEAD 加密；chunk 序号参与 nonce/AAD，检测截断、重排和篡改。
- 明文不落盘；内存只保留固定复制 buffer，不保留完整文件。
- spool 目录专用、权限最小化，不能位于仓库、日志或公共上传目录。
- 单 part、单请求、用户并发和全局磁盘配额均可配置，超限返回 413。
- sweeper 按文件 mtime 清理超过 orphan TTL 的残留；删除失败告警并重试。
- 正常、校验失败、hold 失败、Provider rejected、unknown 和 panic recovery 都必须走 defer 清理。

### 7.4 创建时序

```text
multipart receive
    -> encrypted spool + input manifest + request hash
    -> capability/model/pricing/account selection
    -> DB transaction: task/resource + hold + held event
    -> transition submitting
    -> synchronous Provider.Create/Edit/Character
    -> persist accepted/rejected/unknown result
    -> close readers + delete spool
    -> return local object
```

Provider 调用开始后，使用独立的 submit timeout context；客户端断开不能中止已经开始的上游提交。客户端在 multipart 未接收完成前断开时，不创建任务、不冻结余额。

## 9. 状态机与 Repository 操作

### 9.1 状态

```text
generation:
preparing -> held -> submitting -> queued -> in_progress -> completed
                         |                                |
                         +-> submission_unknown          +-> failed
                                                          +-> cancelled / expired

billing:
none -> held -> capture_pending -> captured
           +-> release_pending -> released
           +-> manual_review

delete:
none -> requested -> deleting -> deleted | delete_failed
```

内部状态只存数据库；OpenAI projection 为 queued/in_progress/completed/failed。

### 9.2 Repository 原子操作

Repository 必须提供：

- `CreateHeldVideoTaskTx`：插入 task、claim idempotency、冻结余额、写 held event，同一事务完成。
- `TransitionVideoTaskTx`：`SELECT ... FOR UPDATE`、校验状态矩阵、版本递增、事件 append。
- `SaveProviderAcceptedTx`：保存 provider task ID、status、content metadata 和 submitting -> queued/in_progress。
- `MarkSubmissionUnknownTx`：保存错误摘要、attempt、unknown 时间和 next review。
- `ClaimVideoTaskLease`/`ReleaseVideoTaskLease`：poll/settlement/delete worker 使用。
- `ListVideoTasksForOwner`：只使用 user_id，稳定 cursor `(created_at,id)`。
- `GetVideoTaskForOwner`、`GetVideoResourceForOwner`：找不到和非本人返回同一个 domain not found。
- `AppendVideoTaskEvent`：Provider event 去重和 unmatched event。
- `MarkVideoBillingPendingTx`、`MarkVideoBillingSettledTx`：和 outbox Complete 事务配合。

所有状态写入都必须通过统一 state transition 函数；禁止 handler 直接更新 status 字段。

## 10. 创建 Saga 与失败恢复

### 10.1 创建步骤

1. 鉴权、功能开关、订阅计费拒绝、内容大小和 callback URL 基础校验。
2. 流式解析 JSON/multipart，构建 input manifest、SHA-256 和 request hash。
3. 通过 capability catalog 校验 operation、input role、MIME、文件大小、size、seconds 和 model。
4. 解析 requested -> public -> channel -> upstream model 映射。
5. 按 Provider、channel、account 选择候选，并在账户级 DB advisory lock 中检查长期视频并发。
6. 解析唯一价格规则和最大 hold；无法求出有限最大成本则 fail closed。
7. 事务创建 task/resource、claim idempotency、冻结余额和 held event。
8. 事务提交后 transition 到 submitting，写 submit attempt/client token。
9. 同步调用 Provider Create/Edit/Character。
10. 成功：保存上游 ID和内容/资源元数据，转 queued/in_progress。
11. 明确拒绝：转 failed，创建 release intent。
12. 结果未知：转 submission_unknown，保留 held，不切换 account、不自动重试。
13. 关闭 reader，删除 spool，返回平台公开对象。

### 10.2 失败点处理

| 失败点 | 本地状态 | 资金动作 | 后续 |
|---|---|---|---|
| body 未接收完 | 无任务 | 无 hold | 删除 spool |
| 解析/capability/定价失败 | 无任务 | 无 hold | 返回 400/413 |
| hold 失败 | 无可提交 task | 事务回滚 | 删除 spool |
| Provider 调用前内部失败 | failed | release_pending | release worker |
| 上游明确拒绝 | failed | release_pending | release worker |
| 上游 timeout/连接断开 | submission_unknown | 保持 held | webhook/search/manual |
| 上游成功但保存响应失败 | stale submitting/unknown | 保持 held | 精确关联或人工 |
| Redis 入队失败 | DB 状态保持 | 不变 | DB sweep 重建 |
| task GET 的临时刷新失败 | 本地状态不回退 | 不变 | 返回快照或 retryable error |

### 10.3 submission_unknown

- 永不通过 prompt hash、时间、模型或用户相似条件猜测上游任务归属。
- OpenAI Adapter 能提供可搜索 client token 时才允许自动 search 收敛；否则 webhook 必须带精确 task ID才能关联。
- 超过 `submission_unknown_quarantine_minutes` 进入管理端 manual review，冻结余额不自动释放。
- 管理员只能执行“已确认未创建 -> release”或“已确认创建 -> 补写 provider ID并继续 polling”，两种操作都写审计事件。
- 不提供无保护的“重放 Create”按钮，避免重复生成。

## 11. Worker、队列和账户亲和

### 11.1 Redis 队列

队列只保存本地 `public_id`，建议 key：

- `video_task:poll:ready`
- `video_task:poll:delayed`
- `video_task:poll:active`
- `video_task:settlement:*`
- `video_task:delete:*`
- `video_task:callback:*`

参考 Batch Image 的 Lua 原子脚本，保证 ready -> active 和 delayed -> ready 不丢任务。Redis 删除后 PostgreSQL sweep 根据 `next_action_at`、pending billing、delete state 和 callback state 重建。

### 11.2 Worker 类型

- `VideoPollingWorker`：按 `next_action_at` lease task，调用 Provider.Get，统一状态收敛。
- `VideoSettlementWorker`：处理 capture/release outbox，调用 hold-aware Complete。
- `VideoDeleteWorker`：处理删除/取消，遵守 account affinity。
- `VideoCallbackWorker`：发送用户 callback，支持租约、指数退避和 quarantine。
- `VideoRecoverySweeper`：找回 expired lease、未知 submitting、Redis 漏投递和孤儿 spool。

Worker 的构造和启动放入 `internal/service/wire.go`，Stop 必须接入现有服务生命周期。

### 11.3 长期并发

- 进入 held 后绑定 Provider/channel/account；绑定后不可负载均衡迁移。
- 账户级 PostgreSQL advisory transaction lock 内计数 `submitting`、`submission_unknown`、`queued`、`in_progress`、`capture_pending`。
- 超过账户或模型 capability 的长期并发返回 429，不创建 task、不冻结余额。
- 请求级 Redis concurrency slot 仅限制上传/查询 HTTP 生命周期，不代表视频长期并发。
- 派生 edit/extend/character operation 默认继承 parent resource 的 account；上传新视频的 edit 作为新任务重新选择兼容 account。

## 12. Provider Webhook 与用户 Callback

### 12.1 Provider Webhook

1. 通过 account/project 选择 secret，读取原始 body。
2. 验签、时间窗校验和 event ID 格式校验。
3. 对 payload 做 URL、token、prompt 和 credential 脱敏。
4. 在事务中按 provider/account/event ID 去重并写 `video_task_events`。
5. 精确关联 task/resource；无法关联的合法事件写 unmatched event。
6. 提交成功后返回 2xx，再唤醒 polling/settlement worker。

Webhook 和 polling 必须调用同一个 `ReconcileProviderObservation`，并用 version/state rank 防止乱序回退。

### 12.2 用户 Callback

- callback target 通过 HTTPS、DNS、解析 IP、端口、私网/metadata 地址和重定向策略校验。
- callback URL 加密存储，payload 只包含平台任务 ID、status、Provider identity、upstream ID和结果 metadata。
- 不包含账户级凭证、任务级 credential value、媒体字节或原始 Provider body。
- 使用独立 HMAC secret，签名头包含 event ID、timestamp 和 body hash。
- completed callback 只有 capture 成功后入可投递队列；failed/cancelled 只有 release/capture 收敛后投递。
- retry 使用 lease、指数退避和 24 小时默认窗口，耗尽进入 quarantine 并告警。

### 13.1 Hold 命令泛化

### 13.2 视频价格快照

任务创建时保存：

- billing unit、estimated/maximum units、actual units。
- requested/public/channel/upstream model。
- operation、size/resolution、规范化 `usage_resolution`、seconds、input type/duration、audio、quality/service tier。
- 命中规则 ID/version、priority、group/account multiplier、customer currency。
- Provider cost currency 和成本快照独立保存。

`resolution` 保存可自定义的定价规则键；`usage_resolution` 只保存合法 `WIDTHxHEIGHT` 或 `NNNp`。结算优先使用 Provider 实际 size，其次使用价格快照的规范值，再从模型名回退；无法可靠确定时不写可选 `usage_logs.video_resolution`，不得截断规则键或因此阻塞 durable settlement。

价格匹配流程：

1. 过滤 Provider/model/operation/规格/输入/音频/时间范围全部匹配的规则。
2. 按 priority 和 specificity 选唯一规则。
3. 同优先级同 specificity 多规则或缺价直接拒绝创建。
4. 根据目录上限计算 hold；不得使用平均成本或无界默认值。

### 13.3 Durable settlement

现有 `usage_billing_outbox` v1 强制 `BalanceCost == ActualCost`，不能直接承载冻结款 capture。新增 payload v2：

- v1 解码和历史事件保持不变。
- Claim 查询同时支持 v1/v2，按 payload version 解码。
- v2 增加 `settlement_scope`、`settlement_ref_id`、hold amount、actual amount、allow over-capture 和 video task ID。

Video settlement Complete 必须在同一 SQL 事务完成：

1. claim `video_task_capture:<local_id>` 或 release request ID。
2. 锁定并调整 `users.balance/frozen_balance`。
3. 退回 hold surplus；实际超过 hold 时在视频 scope 允许原子补扣并记录 overdraft。
4. 更新 API key/account/platform quota。
5. 插入 `usage_logs`，写入视频 billing dimensions。
6. 更新 `video_tasks.billing_state` 和 actual cost。
7. 写 settlement event，完成 outbox。

视频 hold settlement 下 `UsageBillingCommand.BalanceCost` 必须为 0，防止 Complete 同时走普通余额扣款造成双扣。capture/release 的重复执行按 request fingerprint 幂等。

## 14. Content 流式代理

### 14.1 请求流程

```text
GET/HEAD /v1/videos/{local_id}/content?variant=...
    -> owner lookup
    -> completed + captured + not deleted check
    -> immutable provider/account lookup
    -> Provider.OpenContent(variant, Range, conditionals)
    -> response header allowlist
    -> io.CopyBuffer to client
```

### 14.2 HTTP 行为

- `variant` 仅允许 Provider capability 声明的 `video`、`thumbnail`、`spritesheet`。
- 支持 HEAD、单区间 Range、If-Range，正确处理 200、206、416。
- 不读取完整 body，不写临时文件，不放入 Redis/内存缓存。
- 使用固定大小 buffer；客户端断开立即 cancel 上游 context 并关闭 body。
- content proxy 使用独立用户/account semaphore，不占视频生成并发槽。
- 透传 allowlist：`Content-Type`、`Content-Length`、`Content-Range`、`Accept-Ranges`、`ETag`、`Last-Modified`。
- 删除 `Set-Cookie`、Authorization、Provider 内部 request ID、内部存储 header 和任意 redirect。
- 平台生成 Content-Disposition 文件名，响应 `Cache-Control: private, no-store`。
- Provider 内容过期返回 410 `video_content_expired`；非本人仍返回 404。
- 上游 content 401/403/404/5xx 不改变生成/计费状态，只记录 content access event 和返回映射错误。

OpenAI 本身没有可安全下发的共享账户任务凭证，因此默认走平台代理。若 Provider 提供 task-level signed URL，可以按 disclosure policy 返回，但 `/content` 仍必须支持平台代理回退。

## 15. Provider 信息和访问凭证披露

### 15.1 首版策略

首版只开放 `identity` 和 `task_access`：

- `identity`：返回 `provider`、区域和 `provider_task_id`。
- `task_access`：额外返回作用域仅限单任务/单内容且带 `expires_at` 的 token/URL。

系统、分组和账户策略取最严格值，默认 `identity`。每次披露记录不含 value 的审计事件。

### 15.2 禁止事项

以下内容不论 API、callback、错误、日志还是前端埋点都不能返回：

- 共享 OpenAI API key。
- OAuth access/refresh token、SetupToken、session cookie。
- Azure master key、service account JSON、私钥。
- 能访问其他用户任务的 Provider project/account credential。

任务级 access material 如需跨请求保存，使用现有 AES-GCM secret encryptor 保存密文、kind、scope、expires_at；到期由 cleanup worker 清除。包含 credential 的响应强制 `Cache-Control: private, no-store`。

## 23. Grok 耐久兼容与回执生命周期补充（2026-09-05）

- keyed Grok 成功响应不再单独依赖 Redis：`grok_video_jobs` 与 `video_create_intents` 回执同事务保存 Provider task ID、user/API Key/group/account、identity version 和完整冻结计价事实。

- `pending -> billing -> billed/manual_review` 使用数据库租约 owner + epoch fencing；RecordUsage 失败释放为 pending，冻结快照冲突进入 manual review，成功落账后才置 billed。

- migration 258 增加独立 `GrokVideoRecoveryWorker`：数据库 due claim、owner/epoch fencing、pending/unknown 有界退避、done 先持久化再按冻结快照结算、failed/expired/身份异常进入 manual review。用户主动查询不受后台 `next_poll_at` 限制。
- legacy 无幂等 key 路径的读取兼容仍保留；migration 263 已提供证据归档、数据库账号亲和回退和自动计费阻断。由于旧键没有创建期 principal/version 证明，候选不会自动提升或扣费；本补充仍未把 Grok 改造成原生 `video_tasks`。shared intent 管理面已由第 25 节补齐。

## 24. Grok 人工复核实现补充（2026-09-05）

- migration 259 在 `grok_video_jobs` 增加 `review_version`、`billing_attempts` 和 `resolution_review_id`，增加 `waived` 终态及 `grok_video_job_reviews` / `grok_video_job_review_actions`。review 保存完整冻结事实；action 保存请求 hash、actor 和幂等 key。

- 审计表 INSERT/UPDATE/DELETE 均有归因与不可变保护；直接删除被拒绝，父 job 合法清理时通过级联删除。resolution 外键使用延迟检查，避免 job/review 双向引用形成不可清理闭环。

- Admin API 提供只读列表/详情/历史，以及 retry、waive、approve、reject 白名单端点；前端使用独立 Grok durable job 视图，不复用原生 `video_tasks` 的任意 capture/release 控件。

## 25. 共享创建意图冻结与复核实现补充（2026-09-05）

1. `video_create_intents` 的发送合同为 version 1：冻结创建 Key 当时的 Group、实际发送账户、`provider_identity_version` 和规范化的完整计费快照。Repository 同一事务复核 active Key、Key→Group、Account→Group、Grok 平台、当前身份版本和全局 owner；网络发送在事务提交后才允许发生。
2. `dispatching/unknown` 的正常完成和人工完成都必须先存在与冻结快照完全一致的 `grok_video_jobs`；数据库拒绝仅写成功回执、改用当前 Group/价格/计费目标或不同账户的完成。API Key 后续改组不改变历史账务归属。
3. migration 261 增加 review/version/action 表及 `not_created`；migration 262 使用并发唯一索引阻止同一账号的 Provider ID 被两个本地 owner 重复认领。提案和决定绑定不可变 facts；审批动作先于终态写入并在同一事务提交。批准人与提出人必须不同，批准重放不因提出人后来停用而失去幂等性。

## 26. legacy Grok Redis 归档与 fail-closed 接管（2026-09-05）

1. `GrokVideoLegacyCache` 只暴露有界 pending 扫描与既有 session account 读取。Redis `SCAN` 使用字符串游标；每页最多 200 条。Lua 在 Redis 进程内先执行 `STRLEN`，正文超过 64 KiB 时只返回长度和 TTL，避免管理员扫描把异常值完整拉入进程内存。
2. pending key 只接受精确 `user_id:api_key_id:provider_task_id` 结构。Provider ID 使用与 unknown 认领相同的安全字符和凭据检测；重复 JSON 键、无效计价字段或缺少原始时间/分辨率/时长被记录为有界 issue code，不能被默认值伪装成原始事实。
3. Repository 在事务中重新读取 API Key 当前 Group、Group 平台、Account 平台/删除状态/身份版本、Account→Group 与全局 owner 授权，并检查同 owner durable job 和稳定 request ID 的 usage。Redis account ID 只作为待验证输入，不直接成为可信 principal。
4. 导入表的 source key hash、owner、binding、snapshot、首次管理员与首次时间不可变；重复扫描记录当前 active admin 为最近操作者，并仅更新最后观测、TTL、claim/usage 只增事实和 issue 集。Admin DTO 不返回 Redis 键 hash、session hash 或 snapshot hash。
5. lookup 先查 durable job，再查 legacy 导入。候选仅在当前身份版本、Group 和 owner 授权仍匹配时提供固定账号；不满足时返回 reconciliation 冲突。billing claim 只要发现候选就返回未认领，绝不落回旧 Redis claim。
6. 本阶段是“证据保存与风险隔离”，不是“可信账务迁移”。migration 264 只证明当前 identity version 的人工核验 binding，不能证明旧 Redis 作业的创建期 principal；候选提升、已存在 usage/claim 的双人结论和 Redis 最终清理由后续合同完成。

## 27. Provider principal binding 与 alias 撤销合同（2026-09-05）

1. `accounts.provider_principal_binding_id` 只指向当前 `provider_identity_version` 的 active binding。`verified` 必须同时满足 dedicated root account、owner 镜像一致、`isolation_verified_version=provider_identity_version` 和 binding 未撤销；任一缺失在 Go 内存判定与 PostgreSQL 授权函数中都 fail-closed。
2. 提案请求携带 principal kind/value、reason、脱敏 evidence、当前 identity version 和幂等键。服务层规范化官方/自定义 base URL 的 scheme、host、默认端口、路径编码后计算 issuer hash，再按 platform/kind/value 计算 principal hash；原文在调用 Repository 前清空。
3. review、action、binding 和 revocation 都有不可变数据库触发器。批准前再次锁定 account/admin/owner，要求 facts 与当前行完全相等，并拒绝相同 origin/principal 绑定到不同 owner，以及当前数据库中已识别到的 shared/cross-owner credential/project/account alias。
4. 账户身份字段变化继续推进 `provider_identity_version`，自动清除 verified 与当前 binding 指针；普通更新不能设置 binding 或 verified。迁移时任何旧 `verified` 行先降级并发出 scheduler outbox，避免历史人工 SQL 被新合同默认为可信。
5. revocation 是安全单人动作，不等待第二人。事务插入不可变 revocation，撤销同 principal 的所有 active binding，把当前账户全部标记 revoked/不可调度并产生 outbox。状态不可原地恢复；若要重新接入必须创建新的隔离账户/身份。
6. Admin API/UI 只返回 kind、actor、reason/evidence 和 issuer/principal 前 16 位指纹，不返回原值或完整 hash。操作 key 在网络结果不确定时复用，principal 输入成功后立即从组件状态清空，Enter 不会误提交父账户编辑表单。
7. 本合同仍以管理员核对的外部证据为信任根，无法自动证明证据真伪或发现系统外/不同凭据的全部 alias。真实 Provider principal probe、证据签名/账单核验与 legacy 提升必须另行实现和验收。

## 28. multipart 共享创建意图实现补充（2026-09-05）

1. `parseVideoMultipart` 改用 `multipart.Reader.NextRawPart`。只允许单值 `Content-Disposition`/`Content-Type`，拒绝其他 header、重复 header、额外 disposition 参数、控制字符、空文件名、重复 scalar 和 scalar/file 重名；这避免标准 `NextPart` 隐式处理 `Content-Transfer-Encoding` 后破坏规范 hash。
2. 文件 part 在解析时直接调用 `VideoSpoolSession.Store` 写入加密 spool，并复用返回的 `Size`/`SHA256`；scalar 有独立 64 KiB 上限并就地计算摘要。`CanonicalVideoCreateMultipartPartsHash` 规范化 MIME、按字段名稳定排序，并保留同名重复文件的原顺序。
3. 原生与 Composite managed multipart 在完整解析和 spool 成功后调用 `BeginVideoCreateIntentWithHash(..., canonical_multipart_v1)`。该时点早于 `ResolveVideoIngress`、安全审核、`VideoTaskService.Submit`、预算、hold 和 Provider Submit；spool 失败、解析失败或 hash 失败不会领取意图。
4. `executeVideoCreateIntentSession` 统一 JSON/multipart 的 owner、续租、回执与 replay 行为。非 owner 且 intent 已绑定 native task 时调用 native replay closure，使 Service 仅校验同一请求并返回原任务；不得把本地 task replay 错送到 Grok 或再次执行 Provider Create。
5. Composite managed multipart 在解析后调用 `ResolveVideoIngress`。OpenAI 决策继续使用当前加密 spool；Grok 决策由 `videoGrokMultipartBody` 使用 `io.Pipe` 和输入 `Open` 函数流式重建字段/文件，`http.MaxBytesReader` 再对下游读取施加网关上限，且不产生额外明文临时文件。
6. `CanonicalVideoCreateMultipartPartsHash` 不继承 legacy Grok buffered 单文件 20 MiB 限制，避免缩小原生 spool/capability 能力；原有 buffered Grok 路径继续保留其既有限制。两条路径共享请求合同，但能力上限仍由各自入口和 Provider 约束决定。
7. 无新数据库迁移。兼容风险来自旧 writer：旧节点不会在原生 multipart 解析后领取共享意图，可能与新节点重复提交。因此发布必须停止旧 video writer，部署全部新版路由、handler、service 后再恢复创建；数据库不能单独替旧代码补上该前置仲裁。

## 33. correction review 与授权计划实现补充（2026-09-06）

### 33.1 数据模型

- `grok_video_billing_correction_reviews` 保存 job/archive identity、preview/version/hash、source facts、提出/决定管理员和 reason/evidence；`grok_video_billing_correction_review_actions` 保存每次 proposal/approve/reject 的 operation key 与 request hash。
- PostgreSQL 使用 `sha256(convert_to(preview::text,'UTF8'))` 对规范 JSONB 计算 hash，并通过 CHECK 绑定 `preview_hash`；完整 preview/source facts 不能被应用层独立伪造。
- pending review 对 intent 唯一，pending correction 与普通 Grok billing review 双向互斥；同一 intent/job version/preview hash 只允许一个 approved plan。

### 33.2 事务流程

- proposal：锁 job 与 active admin → 幂等重放检查 → 重新加载 archive → 重建 preview → 校验 legacy mismatch 和版本 → 保存数据库计算 hash/source facts → 保存 propose action。
- approve/reject：锁 job、review 与管理员 → 幂等重放检查 → 复核版本/状态；approve 额外要求不同 active admin、提出人仍 active，并重新构建 preview 与 review.preview/source facts 比较 → 更新 review 状态 → 保存 decision action。
- approve 不更新 `grok_video_jobs.review_version` 或 resolution review，不触发资金事务。这样批准计划不会被误表示为已完成更正，后续 apply 必须引用独立 correction execution/adjustment 标识。

### 33.3 接口与显示

- `GET/POST /admin/videos/grok/jobs/:id/correction-reviews` 以及 review approve/reject 接口复用 Admin `If-Match`、个人 actor、严格 JSON、稳定 operation key 和脱敏 evidence 合同。
- DTO 只显示 16 位 archive fingerprint；前端显示冻结 preview、计划状态和双人决定，明确不存在 apply。批准计划后原 job 仍保持 `manual_review`。

## 34. correction apply、ledger 与 projection outbox 实现（2026-09-06）

### 34.1 数据模型

- `grok_video_billing_correction_apply_commands`：每个 review 唯一，保存 intent/review、operation key、request hash、actor、expected job version、reason。command 只能插入一次且不可修改/删除。
- `grok_video_billing_correction_executions`：每个 command/review 唯一，保存 executed by、job version、preview hash、source/current/result facts 和 applied time；仅数据库 trigger 可在创建事务内写入并补全 result facts。
- `grok_video_billing_correction_entries`：以 execution+dimension+target 唯一，记录 source cost delta、applied counter delta、before/after、target/window。它是财务调整总账，不复用原 usage。
- `grok_video_billing_correction_usage_entries`：保存原 usage log ID 以及 actual/desired usage JSON；不更新 `usage_logs`。
- `grok_video_billing_correction_outbox`：execution 唯一，payload 不可变，保存租约、attempt、available/terminal/error；pending 行禁止删除。
- `grok_video_jobs.billing_correction_execution_id`：把 job 终态绑定到唯一 execution，防止仅靠错误字符串或 review status 表示已执行。

### 34.2 数据库执行流程

1. Repository 锁定 job 并先检查 operation-key replay；相同 key/不同 request hash 冲突。
2. 插入 command 前 trigger 验证 active admin、执行人与提出人不同、approved review、job/review version、preview hash、source facts、legacy mismatch 和 review 互斥。
3. command 插入后的 trigger 锁定所有财务目标与原 usage，保存 before facts，创建 execution。
4. 分维调用 balance/subscription/API Key/account/platform 函数。每个函数先锁定当前行、计算方向与窗口实际增量、检查非负和状态转换，再用完整旧值做 CAS update 并写 entry。
5. 保存 correction usage、result facts 和 projection outbox；最后以 job state/version CAS 绑定 execution 并切换 `billed`。任何一步失败，command 及全部副作用随事务回滚。

### 34.3 缓存投影与服务生命周期

- `GrokVideoBillingCorrectionOutboxRepository` 由 `usageBillingRepository` 实现。claim 使用 `FOR UPDATE SKIP LOCKED`，过期租约可被新实例接管；ack 保留 terminal 行，retry 增加 attempt 并释放租约，quarantine 保存有界错误。
- Worker 对 JSON 使用未知字段拒绝和业务不变量校验。缓存操作只做可重放的余额/订阅/rate invalidation、平台 quota 全量刷新和 user auth invalidation，不做增量缓存加减。
- Worker 在财务事务外运行；apply 请求成功表示数据库账务已提交，outbox pending 表示缓存仍待收敛。每个实例均可运行 Worker，无需 leader election。

### 34.4 API 与前端

- `POST /admin/videos/grok/jobs/:id/correction-reviews/:review_id/apply` 使用严格 JSON `{reason}`、`If-Match` 和 `Idempotency-Key`。Service 通过 context 绑定个人 actor 与 intent/version，Repository/数据库继续做最终授权校验。
- review list 可返回 execution、entries 和 usage entry，但 Go DTO 不包含 source facts；完整 archive command/result/fingerprint 不返回。
- 前端只对 approved 且没有 execution 的 plan 显示 apply。按钮对提出人禁用；确认框说明会修改持久化财务计数器且页面不可撤销。执行后展示 ledger，不再显示 apply。
